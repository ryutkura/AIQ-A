# 値オブジェクトの「値は不変」が腑に落ちない（代入と変更の違い）

参照：成瀬允宣『ドメイン駆動設計入門』2.2「値の性質と値オブジェクトの実装」(p.19〜21)、リスト2.7〜2.10

**Q: [[ドメイン駆動設計]]の値オブジェクトの章の出だしで躓いた。「値は不変である」と書いてあるが、`greet = "Hello";` のように普通に変わっているように見える。何が不変なのか？**

---

**A:**

結論から言うと、**不変なのは「値」であって「変数」ではない**。この2つを同じものだと思っていると、本のリスト2.7は「値が変わっている」ようにしか見えない。

## 1. 変数と値は別物

```csharp
var greet = "こんにちは";
greet = "Hello";
```

このコードで起きているのは、

* ×「"こんにちは" という**値そのもの**が "Hello" に書き換わった」
* ○「`greet` という**変数（入れ物）が指している先**が、"こんにちは" から "Hello" に差し替わった」

変数は「中身を入れ替えられる箱」であり、値は「箱に入れる中身」。
箱の中身を入れ替えても、取り出した "こんにちは" という**中身そのものは何も変わっていない**。
本文が「代入によって変更しているのは変数の内容であって、値そのものを変更しているわけではない」と言っているのはこの意味。

## 2. 「もし値が変更できたら」を考えると分かりやすい

本のリスト2.8・2.9はこの区別を突きつけるための**背理法**になっている。仮に値自体を変更するメソッドが存在したとする。

```csharp
var greet = "こんにちは";
greet.ChangeTo("Hello");   // このようなメソッドは本来存在しない
Console.WriteLine(greet);  // Hello
```

`greet` を経由せず、リテラルに直接呼んでも同じ意味になるはずだ。

```csharp
"こんにちは".ChangeTo("Hello");
Console.WriteLine("こんにちは");  // Hello が表示される
```

これはつまり、**ソースコード中のどこに書いた "こんにちは" も、以後すべて "Hello" になる**ということ。
値の世界で「1 を 2 に変更する」が許されれば、以後プログラム中のあらゆる `1` が `2` になる。そんな世界ではもう何も信用して計算できない。

**値が不変だからこそ、`1` はどこで書いても `1` であり、安心して使える。** これが「不変であることが美徳」の意味。

## 3. C# の string は実際に不変

抽象論ではなく、`string` は本当に不変（immutable）として実装されている。

```csharp
var s = "abc";
s.ToUpper();               // 戻り値を捨てているので s は "abc" のまま
Console.WriteLine(s);      // abc

s = s.ToUpper();           // 新しい文字列 "ABC" を作って、変数 s の指す先を差し替えた
Console.WriteLine(s);      // ABC
```

`ToUpper()` や `Replace()` は元の文字列を書き換えず、**新しい文字列を作って返す**。
「変更しているように見える操作」の正体は、いつも **新しい値を作って変数に代入し直すこと**（＝本でいう「交換」）。

## 4. 値オブジェクトも同じルールに従う

値オブジェクトは「システム固有の値」なので、値の性質がそのまま適用される。だから本は `FullName` を次のように扱うことを否定する。

```csharp
var fullName = new FullName("masanobu", "naruse");
fullName.ChangeLastName("sato");   // NG: 値そのものを書き換えている
```

これは `"こんにちは".ChangeTo("Hello")` と同じことを `FullName` でやっている。
`fullName` という変数を通じて誰かに渡した `FullName` インスタンスの中身が、知らないところで別人の名前に変わってしまう。

正しくは、**新しい値を作って変数を差し替える（交換する）**。

```csharp
var fullName = new FullName("masanobu", "naruse");
fullName = new FullName("masanobu", "sato");   // OK: 変更ではなく交換
```

メソッドとして用意する場合も、自分を書き換えず新しいインスタンスを返す形にする。

```csharp
class FullName
{
    public string FirstName { get; }   // setter を置かない（＝生成後に変更できない）
    public string LastName { get; }

    public FullName(string firstName, string lastName)
    {
        FirstName = firstName;
        LastName = lastName;
    }

    // 「変更」ではなく「この値を元にした新しい値」を返す
    public FullName WithLastName(string newLastName)
        => new FullName(FirstName, newLastName);
}

var fullName = new FullName("masanobu", "naruse");
fullName = fullName.WithLastName("sato");   // 代入で受け直すのがポイント
```

`ChangeLastName` という名前をやめて `WithLastName`（あるいは `ToUpper` のような「新しい値を返す」動詞）にするだけで、「これは変更ではなく交換だ」が呼び出し側に伝わる。

## 5. まとめ

| 見え方 | 実際に起きていること | 呼び方 |
| --- | --- | --- |
| `greet = "Hello"` | 変数が指す先の差し替え。値は無傷 | 代入・交換 |
| `greet.ChangeTo("Hello")` | 値そのものの書き換え（存在してはいけない） | 変更 |

* 不変なのは**値**。変数は当然変えられる。だから「値が変わっている」ように見えるだけ。
* 値オブジェクトを作るときは、フィールドを読み取り専用にして setter を置かず、変化させたい時は**新しいインスタンスを返す**。
* 「不変のメリット」は本のコラムの通り、**渡した先で勝手に状態を変えられない**こと。バグの原因になる「いつの間にか変わっていた」が原理的に起きなくなる。

## 補足：リスト2.9の何がマズいのか（読み違えやすい点）

最初に読んだとき、「代入で "こんにちは" を格納できてしまうのがマズい、という話？」と読み違えた。そうではない。
**マズいのは代入の側ではなく、`ChangeTo` の側だけ。** 代入は完全に安全な操作。

### リスト2.9には変数が1つも出てこない

```csharp
"こんにちは".ChangeTo("Hello");
Console.WriteLine("こんにちは");   // Hello が表示される
```

`greet` がいない。ソースコードに直接書いた**文字列リテラルそのもの**にメソッドを呼んでいる。

`ChangeTo` が「値そのものを書き換えるメソッド」だとすると、書き換わる対象は変数ではなく **"こんにちは" という値そのもの**。
値には名前がなく、プログラム全体で共有されている（[[C#]] では実際、同じ内容の文字列リテラルは同一インスタンスに集約される＝インターン）。
したがって2行目の `"こんにちは"` も、別のファイルに書いた `"こんにちは"` も、**以後すべて "Hello" になる**。触ってもいない箇所が変わる。

数値に置き換えると異常さがはっきりする。

```csharp
1.ChangeTo(2);                 // もしこれが許されたら
Console.WriteLine(1 + 1);      // 4 が表示される
```

「1 という値を 2 に変更する」は、辞書の項目を書き換えるような操作。値はそれを受け付けない、というのが「値は不変」の意味。
実際 `string` はそう作られているので `ChangeTo` は存在しない。本は**「もし不変でなかったらこうなる」という架空の世界を見せる背理法**をやっているだけ。

### 実務で効いてくるのはエイリアシング

リテラルの話は理屈っぽいので、`FullName` で同じことをやると実感しやすい。

**代入（安全）:**

```csharp
var a = "こんにちは";
var b = a;          // b も "こんにちは" を指す
a = "Hello";        // a の指す先を差し替えただけ
Console.WriteLine(b);   // こんにちは  ← b は無傷
```

**変更（危険）:** `FullName` が可変（`ChangeLastName` を持つ）だと、

```csharp
var a = new FullName("masanobu", "naruse");
var b = a;                       // b も同じインスタンスを指す
a.ChangeLastName("sato");        // 値そのものを書き換えた
Console.WriteLine(b.LastName);   // sato  ← b は触っていないのに変わる
```

`b` をどこかのメソッドに渡していたら、相手が持っている名前が知らないうちに別人になる。
コラム「不変のメリット」の「自身のあずかり知らぬところで状態の変更をされ、意図せぬ挙動となりバグを引き起こす」はこの現象のこと。

**代入は他の誰にも影響しない。変更は同じ値を見ている全員に影響する。**
これが両者を区別する実務的な理由であり、値オブジェクトを不変にすれば下のパターンは原理的に起こせなくなる。

## 補足2：`var b = a;` は「中身のコピー」ではない（最大の躓きどころ）

> `a` に masanobu, naruse を入れて `b` にコピーした。`a` を変えたら `a` = masanobu, sato で
> `b` = masanobu, naruse じゃないのか？

ここで詰まった。これは[[ドメイン駆動設計]]の話ではなく **[[C#]] の言語仕様（参照型）の話**。
結論：**`var b = a;` は中身のコピーではなく「矢印（住所）のコピー」**。

### new した時点で実体は1個しかない

```csharp
var a = new FullName("masanobu", "naruse");
```

```
   a ──┐
       ▼
     ┌──────────────────┐
     │ FullName の実体   │   ← new が作った箱。これが1個だけ
     │ First: masanobu  │
     │ Last : naruse    │
     └──────────────────┘
```

変数 `a` が持っているのは箱そのものではなく、**箱の住所**。

```csharp
var b = a;
```

ここで新しい箱は作られない。コピーされるのは住所だけ。

```
   a ──┐
       ├──▶ ┌──────────────────┐
   b ──┘    │ First: masanobu  │   ← 実体はやはり1個
            │ Last : naruse    │
            └──────────────────┘
```

したがって `a.ChangeLastName("sato");` は変数 `a` には一切触れていない。
**矢印をたどった先の箱の中身を書き換えている。** 箱は1個しかないので `b` からのぞいても `sato` になる。
「参照先のデータを変えた」という理解で正しい。**箱が1個しかないことに気づいていない**のが誤解の原因だった。

### 代入は矢印の付け替えなので波及しない

```csharp
a = new FullName("masanobu", "sato");
```

こちらは新しい箱を作って `a` の矢印を向け直す操作。

```
   a ──────▶ ┌──────────────────┐
             │ First: masanobu  │   ← 新しい箱
             │ Last : sato      │
             └──────────────────┘

   b ──────▶ ┌──────────────────┐
             │ First: masanobu  │   ← 元の箱は無傷
             │ Last : naruse    │
             └──────────────────┘
```

直感どおりの結果（`a` は sato、`b` は naruse）になるのはこちら。
**直感が正しいのは代入の方で、`ChangeLastName` の方が直感を裏切る**という構図。

### なぜ int や string では引っかからないのか

```csharp
int a = 1;
int b = a;   // これは本当に中身のコピー
```

`int` などの**値型（struct）**は代入で中身が丸ごとコピーされるため、矢印の共有が起きない。
一方 `class` は**参照型**なので住所のコピーになる。`FullName` は class。

`string` も参照型（住所のコピー）だが、**中身を書き換えるメソッドが1つも用意されていない**ので、
共有されていても誰も困らない。これが「不変だから安全」の正体。

### 実際に怖いのは `var b = a` ではなく引数渡し

`var b = a;` と明示的に書く場面は少ないが、次は日常的に起きる。

```csharp
var fullName = new FullName("masanobu", "naruse");
SendMail(fullName);                   // 中で ChangeLastName されたら
Console.WriteLine(fullName.LastName); // 呼び出し側の値が変わっている
```

引数に渡す＝住所を渡すことなので `var b = a` と同じ状況。
`FullName` を不変（setter なし・`ChangeXxx` なし）にしておけば、**渡した先が何をしようと絶対に壊せない。**
これがコラム「不変のメリット」の言っている内容。

## 補足3：結局この章は何を言っていたのか

自分の理解：「int, double のノリでクラスのフィールドを扱ったら知らずに壊す」——ほぼ合っているが、向きを直すとスッキリする。

> **「int のノリで扱ったら壊れる」ではなく、「int のノリで扱えるようにクラス側を作ってやる必要がある」。**

`int` が安心なのは、次の2つが揃っているから。

1. **書き換えるメソッドが存在しない**（`1` を `2` にできない）
2. **代入すると中身がコピーされる**（値型なので共有が起きない）

素の `class` はどちらも持っていない。

| | 書き換え手段 | 代入の挙動 | 結果 |
| --- | --- | --- | --- |
| `int` | 無い | コピー | 安全 |
| `string` | 無い | 住所コピー（共有） | **安全**（共有されても壊せないため） |
| 可変な `class` | ある | 住所コピー（共有） | 壊れる |

注目すべきは `string` の行で、**共有そのものは悪ではない。**
共有されていても書き換え手段が無ければ誰も困らない。危険なのは「共有される」×「書き換えられる」の掛け算のときだけ。

そして共有をやめるのは現実的でない（引数に渡すたびに共有が起きる）ので、**書き換え手段の方を潰す**＝不変にする。
これが値オブジェクト。読むだけなら何をしても壊れない。

> 値オブジェクト ＝ 自作のクラスを `int` や `string` と同じ安心感で扱えるようにしたもの

### record を使うとほぼ自動で揃う

```csharp
public record FullName(string FirstName, string LastName);

var a = new FullName("masanobu", "naruse");
var b = a with { LastName = "sato" };   // a は無傷、b が新しい値
Console.WriteLine(a == new FullName("masanobu", "naruse"));  // True（中身で比較）
```

`with` 式が本でいう「交換」、`==` が中身で比較されるのが「等価性によって比較される」。
2.2章の3つの性質がそのまま言語機能になっている（本は原理を見せるため手書きしている）。

## 補足4：値オブジェクトを使うモチベーション4つは「自己文書化」の話なのか

本で紹介される4つ（表現力を増す／不正な値を代入させない／誤った代入を防ぐ／ロジックの散在を防ぐ）を読んで、
「単なる変数だと分からないことがコードを読めば分かるようになる、という話か」と理解した。
半分合っているが、半分はもっと強いことを言っている。
**「読めば分かる」で止まらず、「読まなくても壊せない」ところまで行くのが本命。**

| モチベーション | 効き方 |
| --- | --- |
| 表現力を増す | 読めば分かる（ドキュメント） |
| 不正な値を代入させない | **読まなくても壊せない**（実行時に強制） |
| 誤った代入を防ぐ | **読まなくても壊せない**（コンパイル時に強制） |
| ロジックの散在を防ぐ | 読む場所・直す場所が1箇所になる |

### 命名やコメントと決定的に違う点

命名規則・コメント・仕様書は**破っても動く。だからいつか破られる。** 型は破ると動かない。

```csharp
// string のまま
void Register(string userId, string userName) { }
Register(name, id);          // 引数の順番を間違えた → コンパイルが通る → 本番で事故

// 値オブジェクト
void Register(UserId userId, UserName userName) { }
Register(name, id);          // コンパイルエラー。実行すらできない
```

レビューで見落とすタイプのミスを機械が止めてくれる。「気をつける」を「気をつけなくてよくする」に変換している。

不正な値の方も同じ構図。

```csharp
class ProductCode
{
    public string Value { get; }
    public ProductCode(string value)
    {
        if (string.IsNullOrEmpty(value)) throw new ArgumentException(nameof(value));
        if (value.Length != 8) throw new ArgumentException("8桁である必要があります");
        Value = value;
    }
}
```

効き目は「バリデーションが書いてある」ことではなく、
**「不正な `ProductCode` のインスタンスはこの世に存在し得ない」という保証が手に入る**こと。
受け取った側は二度とチェックしなくていい。`string` で回していると、関数の入口ごとに
「こいつ検証済みだっけ？」と考え続けることになる。

### 4つ目は将来の自分への効き目

`string` で持っていると、桁数チェックが3箇所、書式変換が2箇所……と散らばる。
仕様が変わったとき grep で全部見つけられる自信はまずない。
**1箇所に集めておくと「grep漏れ」という事故カテゴリごと消える。**
読みやすさの話ではなく、変更コストの話。

### 「流石にやりすぎだろ」と感じたときの線引き

その感覚は正しい。全部を値オブジェクトにするのはやりすぎなので、基準を持っておく。

作る価値があるもの:

* **ルール（制約）がある** — 桁数、形式、範囲、必須
* **取り違えると事故になる** — ID系、金額と数量、日付の開始と終了
* **付随する振る舞いがある** — 書式化、換算、比較、加算

逆に、**何の検証も振る舞いも持たない素通しのラッパー**はコード量が増えるだけ。
ループカウンタやその場限りの計算途中の数値も同様。

> 迷ったときの判断基準：**この型に、いつか `if` を1個足したくなるか？**
> 足したくなるなら作る価値がある。絶対に足さないなら `int` のままでいい。

## 関連

* この後の節「交換が可能である」「等価性によって比較される」は、どちらもこの不変性を前提にした話になる。交換＝代入で差し替えること、等価性＝同じ属性なら同じ値として扱うこと。
* 値オブジェクトと対になる概念が [[エンティティ]]。こちらは「同一性（ID）」で区別され、状態が変わってもよい。両者の使い分けは次章以降のテーマ。
