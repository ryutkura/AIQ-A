# 技術ノート作成ルール

> **このファイルの使い方**
>
> これは**別のリポジトリ（勉強用・開発用）に置くための指示書**です。
> このファイル名のままでは、どのエージェントも自動では読みません。
> 使う時は、そのリポジトリのルートへ **`CLAUDE.md` という名前でコピー**してください。
>
> ```
> 勉強用リポジトリ/
>   CLAUDE.md      ← このファイルをコピーしてリネーム
>   AGENTS.md      ← 下記の1行だけの新規ファイル（Claude以外も使う場合のみ）
>   technote/
> ```
>
> `AGENTS.md` の中身は次の1行だけにします。**全文をコピーしないでください**
> （2箇所に同じ内容があると、片方だけ直して食い違うため）。
>
> ```
> このリポジトリのルールは CLAUDE.md に書いてあります。作業前に必ず読んでください。
> ```
>
> **`CLAUDE.md` と `technote/` は必ず同じ階層に置いてください。**
> 下記のパスは全て `CLAUDE.md` のある場所からの相対パスです。
>
> ここで書かれたノートは、後でナレッジベースへ移植されます。
> 移植を「フォルダのコピー + コマンド1本」で終わらせるため、以下の形式を守ってください。

---

## 1. どこに書くか

質問と回答は、必ず `technote/` 配下に Markdown で残してください。
**フォルダは移植先と同じ構造にします。** これにより移植時の仕分けが不要になります。

| 内容 | 置き場所 |
| --- | --- |
| 概念・仕組みについての質問 | `technote/<分野>/`（例: `technote/programming/`） |
| エラーで詰まった話 | `technote/troubleshooting/` |

**この2つを混ぜないでください。** フラットに溜めると、移植時に1ファイルずつ開いて
仕分ける羽目になり、確実に破綻します。仕分けは「書く時」に済ませます。

### ファイル名

* 概念の質問 … 内容が分かる名前。日付は付けない
  例: `argument_passing_by_reference.md`
* エラーの記録 … **日付を前置**する（エラーは概念ではなくイベントのため）
  例: `2026-08-12_module-not-found.md`

---

## 2. frontmatter（必須）

先頭に必ず付けてください。これが無いと移植先で絞り込み・集計ができません。

**概念の質問:**

```
---
type: qa
tags: [python, oop]
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: seed
---
```

**エラーの記録:**

```
---
type: troubleshoot
tags: [python]
error: "エラーメッセージの特徴的な部分"
env: "Windows 11 / Python 3.12"
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: solved      # solved | workaround | unsolved
stuck_time: 40min
---
```

`error` と `stuck_time` は後から「自分がどこで時間を溶かしているか」を集計するために使います。
面倒でも埋めてください。ここを省くと、傾向分析が一切できなくなります。

---

## 3. 本文に必ず含めること

### 3-1. 該当するコードを本文に貼る（最重要）

**ノートは、それ単体で意味が通る状態にしてください。**

移植先にはソースコードを持ち込みません。「`main.py` の 42行目が」と書いても、
移植後には参照先が存在せず、何の話か分からない抜け殻になります。

```python
# ← このように、該当箇所を本文のコードブロックとして貼る
def f(lst):
    lst.append(1)
```

「上のコード」「さっきのファイル」「先ほどの実行結果」といった、
**その場の文脈に依存する指示語を使わないでください。**

### 3-2. エラーは全文をテキストで

要約も、スクリーンショットでの代用も禁止です。
後日また同じエラーに遭遇した時、**エラー文をそのまま全文検索して過去の記録に辿り着く**のが
このノートの最大の使い道であり、画像は検索にかかりません。

スクリーンショットを**添える**のは歓迎です（GUIの画面状態など）。ただしテキストの代わりにはしないこと。

### 3-3. 「なぜ詰まったか」を書く（`type: troubleshoot` の場合）

解決策だけ書くと、ただの作業ログになります。知識になるのは次の2つです。

1. **試したことと、なぜそう考えたか（仮説）、なぜダメだったか**
   これが無いと、次回また同じ袋小路に入ります。
2. **どんな思い込みが判断を誤らせたか**
   「知らなかった」で終わらせず、1〜2文で言語化してください。
   例:「`docker start` がコンテナを作り直すと思い込んでいた」

---

## 4. 記録しないこと

### 4-1. 絶対に書いてはいけない

* **APIキー、トークン、パスワード、接続文字列**
  ノートはリポジトリに残り、後で別の場所へ移植されます。伏字にするか、丸ごと省いてください。
* 個人情報、業務上の非公開情報

### 4-2. ノイズなので省く

* **AIの前置きと相槌** — 「素晴らしい質問ですね！」「なるほど、確かにその通りです」など。
  回答の中身だけを残してください。
* **教科書本文の丸写し** — 引用は最小限にし、理解した内容を自分の言葉で書く。
* **数百行のログ全文** — 原因に関係する部分だけに絞る。
* **環境固有の絶対パス** — `C:\Users\ryutk\...` は `<プロジェクトルート>/...` のように一般化する。
* **会話の往復そのもの** — 「Q: 〜 A: 〜 Q: やっぱり 〜」という生ログではなく、
  **結論が分かる1本の記事**に整形してください。読み返すのは半年後の自分です。

### 4-3. そもそもノートにしない

タイポ、インデントミス、変数名の打ち間違いなど、**使い捨ての詰まり**は記録不要です。

判断基準は **「半年後の自分がもう一度読む価値があるか」** の一点。
無いなら書かない。全部残すと、移植先のナレッジが薄まります。

---

## 5. 書き終わりの条件

以下を満たして初めて「書けた」とみなしてください。

- [ ] frontmatter がある（`type` / `tags` / `created` / `status`）
- [ ] `technote/` 配下の、正しいフォルダにある
- [ ] 該当コードが本文のコードブロックとして含まれている
- [ ] 「上のコード」「さっきの」など、文脈依存の指示語が無い
- [ ] エラーがある場合、全文がテキストで貼られている
- [ ] `type: troubleshoot` の場合、「なぜ詰まったか」が埋まっている
- [ ] 秘密情報・絶対パスが含まれていない
- [ ] AIの前置きや相槌が削られている

---

## 6. 移植手順（ナレッジベース側で実行）

`technote/` 配下のフォルダを、移植先の同名フォルダへコピーしたあと、移植先で以下を順に実行します。

```bash
python tools/link_keywords.py --link --write
python tools/make_concepts.py --write
python tools/add_frontmatter.py --write
python tools/make_moc.py --write
```

**ソースコード（`.py` などのファイル）は移植しません。** 移植するのは `technote/` の Markdown だけです。

移植先のツールは、ファイル名や章立ての規則を見ていません。
frontmatter と本文中のリンクだけを見ているので、**この形式さえ守っていれば命名は自由**です。
