## 名前と参照

### 一言でいうと

Pythonの変数は、値を入れておく**箱ではなく**、オブジェクトに貼る**名札**だ。
`b = a` は中身をコピーしない。`a` が貼られているオブジェクトに、`b` という名札をもう1枚貼るだけだ。

### なぜ必要か・どこで効くか

この理解が無いと、次のようなバグの原因が見えない。

- 関数にリストを渡したら、関数の中の書き換えが呼び出し元にまで漏れた
- LLMに渡す `messages` を「コピーして」から加工したつもりが、元の会話履歴まで変わっていた
- 設定の辞書を複数のエージェントに配ったら、1つの変更が全部に伝わった

どれも「2つの名前が、実は同じ1つのオブジェクトを指していた」ことが原因だ。

### 本体

#### 箱モデルと名札モデル

多くの入門書は、変数を「値を入れる箱」と説明する。この説明だと、`b = a` は「`a` の箱の中身を `b` の箱にコピーする」ことになる。

```
箱モデル（Pythonでは間違い）

  a: [ [1, 2, 3] ]
  b: [ [1, 2, 3] ]   ← 中身が別々にコピーされている、と考える
```

Pythonの実際の動きは名札モデルだ。

```
名札モデル（Pythonの実際）

  a ──┐
      ├──→ [1, 2, 3]   ← オブジェクトは1つだけ
  b ──┘
```

確かめてみよう。

```python
a = [1, 2, 3]
b = a
b.append(4)
print(a)          # [1, 2, 3, 4]  ← a から見ても変わっている
print(a is b)     # True          ← 同じオブジェクト
print(id(a), id(b))  # 同じ数字が2回出る
```

`id()` はオブジェクトの「住所」のような番号を返す。`a` と `b` の `id` が同じということは、名札が2枚、同じオブジェクトに貼られているということだ。

#### 「オブジェクト」とは何か

Pythonでは、**値はすべてオブジェクト**だ。リストだけでなく、整数の `1` も、文字列の `"hi"` も、関数も、クラスそのものもオブジェクトだ。
オブジェクトはメモリ上のどこかに置かれた実体で、次の3つを持つ。

| 持っているもの | 確かめ方 | 例 |
|---|---|---|
| 同一性（どの実体か） | `id(x)` | `140234...` |
| 型（何の種類か） | `type(x)` | `<class 'list'>` |
| 値（中身） | `print(x)` | `[1, 2, 3]` |

変数（名前）の方は、型も値も持っていない。持っているのは「どのオブジェクトに貼られているか」という情報だけだ。
だから Python では、同じ名前に別の型の値を代入し直せる。

```python
x = 1        # x は int オブジェクト 1 に貼られている
x = "hi"     # x を剥がして、str オブジェクト "hi" に貼り直した
```

#### 代入は「名札の貼り替え」

`=` が行うのは、右辺のオブジェクトに左辺の名札を貼ることだけだ。オブジェクトは作られないし、コピーもされない（右辺がオブジェクトを新しく作る式なら、作られるのは右辺の評価の結果だ）。

```python
a = [1, 2, 3]   # [1, 2, 3] というリストが作られ、a が貼られる
b = a           # 新しいリストは作られない。b も同じリストに貼られる
a = [9]         # [9] という別のリストが作られ、a はそちらに貼り替えられる
print(b)        # [1, 2, 3]  ← b は元のリストに貼られたまま
```

最後の `a = [9]` で `b` が変わらないことに注意しよう。`a` の名札を剥がして別のオブジェクトに貼り替えただけで、元のリストには何もしていない。

#### 関数の引数も「名札の貼り替え」

関数を呼ぶとき、引数も同じ仕組みで渡される。関数の仮引数という名札が、渡したオブジェクトに貼られる。

```python
def add_system_prompt(messages):
    messages.insert(0, {"role": "system", "content": "あなたは親切です"})
    return messages

history = [{"role": "user", "content": "こんにちは"}]
sent = add_system_prompt(history)
print(len(history))   # 2  ← 呼び出し元の history まで変わっている
print(sent is history)  # True
```

関数の中の `messages` と、外の `history` は、同じリストに貼られた2枚の名札だ。だから `insert` の結果が外からも見える。
LLMアプリでは、会話履歴をあちこちの関数に渡すので、これは本当によく起きる。

元を変えたくないなら、**コピーを明示的に作る**。

```python
def add_system_prompt(messages):
    new = [{"role": "system", "content": "あなたは親切です"}, *messages]  # 新しいリストを作る
    return new
```

#### Java と比べると

Java を知っているなら、**Pythonの変数はすべて Java の参照型の変数**だと思えばよい。

| | Java | Python |
|---|---|---|
| `int` などの基本型 | 箱に値が直接入る | **無い**。整数もオブジェクトで、名前はそれを参照する |
| `List` などのオブジェクト | 変数は参照を持つ | 同じ |
| `b = a` | 参照のコピー（オブジェクトは1つ） | 同じ |

Java の `int` のような「箱に直接入る値」が Python には無い。ここが一番の違いだ。ただし、整数や文字列は後で説明するイミュータブルなので、箱モデルで考えても結果がずれることはほとんど無い。ずれが表に出るのは、リストや辞書のようなミュータブルなオブジェクトを扱うときだ。

### よくある誤解

**`ref.assign-copies`：代入や引数渡しで、オブジェクトの中身がコピーされると思っている**

- 思い込み：`b = a` や `f(a)` で、`a` の中身の複製が作られる
- 実際：名札が1枚増えるだけ。オブジェクトは1つのまま
- 確かめるコード：

  ```python
  a = [1]
  b = a
  print(a is b)   # True なら、同じオブジェクト
  ```

### 理解度チェック

- **言える**：`b = a` の直後、`a` と `b` はどういう関係にあるか
- **説明できる**：箱モデルと名札モデルの違いを、図を描いて説明する。`a = [9]` で `b` が変わらない理由も含めて
- **使える**：次のコードの出力を予測する

  ```python
  x = [1, 2]
  y = x
  y = y + [3]
  y.append(4)
  print(x, y)
  ```

## ミュータブル

### 一言でいうと

オブジェクトには、**作った後に中身を書き換えられるもの（ミュータブル）**と、**書き換えられないもの（イミュータブル）**がある。
リスト・辞書・集合はミュータブル。整数・文字列・タプルはイミュータブル。

名札モデルと組み合わせると、こうなる。**ミュータブルなオブジェクトに名札が複数貼られていると、どの名札から書き換えても、全部の名札から変化が見える。**

### なぜ必要か・どこで効くか

「名前と参照」だけでは、バグは起きない。名札が2枚あっても、誰も中身を書き換えなければ問題にならないからだ。
バグが起きるのは、**共有されたオブジェクトを、誰かが書き換えたとき**だ。q1 も q3 も、まさにこの形をしている。

- q1：全インスタンスが1つのリストを共有していて、`append` で書き換えた
- q3：全インスタンスが1つのリスト（デフォルト引数）を共有していて、`append` で書き換えた

### 本体

#### 種類の一覧

| ミュータブル（書き換えられる） | イミュータブル（書き換えられない） |
|---|---|
| `list` | `int`、`float`、`bool` |
| `dict` | `str` |
| `set` | `tuple` |
| 自分で作ったクラスのインスタンス（普通は） | `frozenset` |
| | `None` |

「書き換えられない」とは、そのオブジェクトの値を変える操作が存在しないという意味だ。文字列には `append` が無いし、`s[0] = "x"` もエラーになる。

```python
s = "hello"
s.upper()     # "HELLO" という新しい文字列を返す。s 自体は変わらない
print(s)      # hello
```

#### 2種類の操作：名札を動かすか、中身を変えるか

この章で一番大事な区別がこれだ。

| 操作 | 何が起きるか | 例 |
|---|---|---|
| **名札の貼り替え**（rebind） | 名前が別のオブジェクトを指すようになる。元のオブジェクトは無傷 | `x = ...`、`x = x + [1]` |
| **中身の書き換え**（mutate） | オブジェクト自体が変わる。同じオブジェクトを指す全員に見える | `x.append(1)`、`x[0] = 1`、`x["k"] = 1`、`x.sort()` |

```python
a = [1, 2]
b = a

b = b + [3]    # 名札の貼り替え：b + [3] で新しいリストができ、b はそちらへ
print(a)       # [1, 2]  ← a は無傷

b = a
b.append(3)    # 中身の書き換え：a と b が共有するリストそのものが変わる
print(a)       # [1, 2, 3]
```

`b = b + [3]` と `b.append(3)` は、見た目の結果（`b` の中身）は同じだ。でも、ほかの名札への影響がまったく違う。

#### 落とし穴：`+=` はどちらなのか

`+=` は型によって振る舞いが変わる。

```python
n = 1
m = n
n += 1         # int はイミュータブルなので、新しいオブジェクト 2 を作って n を貼り替える
print(m)       # 1

a = [1]
b = a
a += [2]       # list は「その場で書き換える」+= を持っている
print(b)       # [1, 2]  ← b にも見える
```

リストの `+=` は `extend` と同じで、中身の書き換えだ。「`+=` は `x = x + ...` の省略形」と覚えていると、ここでつまずく。

#### イミュータブルの中にミュータブルが入っていると

タプルはイミュータブルだが、それは「どのオブジェクトを指しているか」が変えられないという意味だ。指している先がリストなら、そのリストの中身は変えられる。

```python
t = ("設定", [1, 2])
t[1].append(3)   # タプルが指しているリストの中身を書き換えた
print(t)         # ('設定', [1, 2, 3])
```

#### コピーの作り方：浅いコピーと深いコピー

共有を断ち切りたいときは、コピーを明示的に作る。

```python
import copy

a = [[1, 2], [3, 4]]

b = a.copy()          # 浅いコピー（list(a)、a[:] も同じ）
b.append([5])
print(a)              # [[1, 2], [3, 4]]  ← 外側のリストは別物になった
b[0].append(99)
print(a)              # [[1, 2, 99], [3, 4]]  ← でも内側のリストは共有されたまま

c = copy.deepcopy(a)  # 深いコピー：内側まで全部複製する
c[0].append(100)
print(a)              # [[1, 2, 99], [3, 4]]  ← 影響なし
```

```
浅いコピー                      深いコピー
a ──→ [ ● , ● ]                a ──→ [ ● , ● ]
         │   │                          │   │
         ▼   ▼                          ▼   ▼
       [1,2] [3,4]                    [1,2] [3,4]
         ▲   ▲
         │   │                    c ──→ [ ● , ● ]
b ──→ [ ● , ● ]                          │   │
                                         ▼   ▼
                                       [1,2] [3,4]  ← 中身まで別物
```

LLMアプリの `messages` は「辞書のリスト」なので、浅いコピーでは中の辞書が共有されたままになる。中の辞書まで書き換えるなら `deepcopy` か、新しい辞書を作り直す。

### よくある誤解

**`mut.shared-unaware`：同じリストを複数の名前が指しているとき、片方の書き換えがもう片方に見えることを想定していない**

- 思い込み：インスタンスや変数が別なら、リストも別々にあるはず
- 実際：リストは作った回数しか存在しない。`[]` を1回しか評価していなければ、リストは1つだけ
- 確かめるコード：怪しい2つの名前を `is` で比べる。`True` なら共有している

**`mut.rebind-vs-mutate`：名札の付け替え（=）と、オブジェクトの書き換え（append など）を区別していない**

- 思い込み：`b = b + [3]` も `b.append(3)` も同じこと
- 実際：前者は `b` だけが新しいリストへ移る。後者は共有しているリストそのものが変わる
- 確かめるコード：上の「2種類の操作」のコードを実行し、`a` の出力を比べる

### 理解度チェック

- **言える**：`list`、`str`、`tuple`、`dict`、`int` をミュータブルとイミュータブルに分ける
- **説明できる**：`x += 1`（`x` は int）と `lst.append(1)` で、名札とオブジェクトにそれぞれ何が起きるか
- **使える**：次の関数は、呼び出し元の設定を壊してしまう。壊さないように直す

  ```python
  def with_temperature(config, t):
      config["temperature"] = t
      return config
  ```

## 同一性と同値性

### 一言でいうと

2つのオブジェクトを比べる方法は2つある。

- **同一性**（`is`）：**同じ1つのオブジェクトか**。名札が同じ実体に貼られているか
- **同値性**（`==`）：**等しいとみなせるか**。何をもって等しいとするかは、クラスの `__eq__` が決める

### なぜ必要か・どこで効くか

q7 では「中身が同じなら `==` は `True`」と考えた。でも、`__eq__` を書いていない普通のクラスの `==` は `is` と同じ動きをする。
ログの重複除去、キャッシュのキー、テストの `assert a == b` は、どれも `==` の意味に頼っている。意味を取り違えると、重複が消えない、キャッシュに当たらない、テストが通らない、といったことが起きる。

### 本体

#### `is` と `==` の違い

```python
a = [1, 2]
b = [1, 2]      # 中身は同じだが、別に作ったリスト
c = a

print(a == b)   # True   ← list の __eq__ は中身を比べる
print(a is b)   # False  ← 別のオブジェクト
print(a is c)   # True   ← 同じオブジェクト
```

```
a ──→ [1, 2]  ←── c        a is c  → True
b ──→ [1, 2]               a is b  → False（実体が別）
                           a == b  → True（中身が等しい）
```

#### `==` は `__eq__` を呼んでいる

`a == b` と書くと、Python は内部で `a.__eq__(b)` を呼ぶ。名前の前後に `__` が付いたこういうメソッドを**特殊メソッド**（dunder メソッド）と呼ぶ。演算子や組み込み関数は、特殊メソッドの呼び出しに書き換えられている。

| 書き方 | 呼ばれる特殊メソッド |
|---|---|
| `a == b` | `a.__eq__(b)` |
| `len(a)` | `a.__len__()` |
| `print(a)`、`str(a)` | `a.__str__()`（無ければ `__repr__`） |
| `a + b` | `a.__add__(b)` |
| `x in a` | `a.__contains__(x)` |
| `hash(a)` | `a.__hash__()` |

リストや文字列は「中身を比べる `__eq__`」を持っている。だから `[1, 2] == [1, 2]` は `True` になる。

#### 自分で作ったクラスの `==`

`__eq__` を書いていないクラスは、すべてのクラスの祖先である `object` の `__eq__` を使う。`object.__eq__` は**同一性**を比べる。

```python
class Msg:
    def __init__(self, role, content):
        self.role, self.content = role, content

print(Msg("user", "hi") == Msg("user", "hi"))   # False
```

Python は「何をもってこの2つの `Msg` を等しいとするか」を知らない。役割だけ同じなら等しいのか、ID を持たせるなら ID で比べるのか、決めるのはクラスを作った人だ。だから既定では、一番安全な「同じ実体か」で比べる。

中身で比べたいなら `__eq__` を書く。

```python
class Msg:
    def __init__(self, role, content):
        self.role, self.content = role, content

    def __eq__(self, other):
        if not isinstance(other, Msg):
            return NotImplemented          # 比べ方が分からない相手には NotImplemented を返す
        return (self.role, self.content) == (other.role, other.content)

print(Msg("user", "hi") == Msg("user", "hi"))   # True
```

#### dataclass は `__eq__` を自動で作る

`@dataclass` を付けると、フィールドを順に比べる `__eq__` が自動で作られる。さらに `__init__` と、見やすく表示するための `__repr__` も作られる。

```python
from dataclasses import dataclass

@dataclass
class DMsg:
    role: str
    content: str

print(DMsg("user", "hi") == DMsg("user", "hi"))   # True
print(DMsg("user", "hi"))                         # DMsg(role='user', content='hi')
```

#### Java と比べると

| | Java | Python |
|---|---|---|
| 同じ実体か | `a == b`（参照型） | `a is b` |
| 等しいとみなせるか | `a.equals(b)` | `a == b` |
| 既定の「等しい」 | `Object.equals` は参照の比較 | `object.__eq__` は同一性の比較 |

**Java の `==` と Python の `==` は意味が違う。** Java の `==` に当たるのは Python の `is` だ。ただ、「equals を自分で書かないと参照の比較になる」という点は、Java と Python で同じだ。

#### ハッシュと集合：重複除去で効いてくる

重複を消すのに `set` を使うことが多い。`set` や辞書のキーは、`__eq__` に加えて `__hash__`（ハッシュ値）を使う。約束事は1つだ。

> **等しい（`==` が True）オブジェクトは、同じハッシュ値を持たなければならない。**

`@dataclass` は既定で `__eq__` を作り、その代わりに `__hash__` を `None` にする。中身を書き換えられるオブジェクトのハッシュ値が変わると、集合が壊れてしまうからだ。そのため、そのままでは `set` に入れられない。

```python
@dataclass
class DMsg:
    role: str
    content: str

{DMsg("user", "hi")}    # TypeError: unhashable type: 'DMsg'

@dataclass(frozen=True)  # イミュータブルにすると __hash__ も作られる
class FMsg:
    role: str
    content: str

print(len({FMsg("user", "hi"), FMsg("user", "hi")}))   # 1  ← 重複が消えた
```

ここでも「ミュータブルかどうか」が効いている。第1章の概念はこうしてつながっている。

#### `is` を使うべき場面、使ってはいけない場面

- **使うべき**：`None` との比較。`if x is None:` と書く。`None` はプログラム全体に1つしか無いオブジェクトなので、同一性で比べるのが正確で速い
- **使ってはいけない**：数値や文字列の比較。CPython は小さな整数（-5〜256）などを使い回すので、`a is b` がたまたま `True` になることがある。でもそれは実装の都合で、保証されていない。値を比べるときは必ず `==` を使う

### よくある誤解

**`eq.always-content`：`==` はどんなオブジェクトでも中身（属性の値）を比べてくれると思っている**

- 思い込み：属性の値が全部同じなら、`==` は `True` になる
- 実際：`__eq__` を定義していないクラスの `==` は、`is` と同じく同一性を比べる
- 確かめるコード：自分のクラスで `print(type(obj).__eq__ is object.__eq__)` を実行する。`True` なら `__eq__` を定義していない

**`eq.dataclass-identity`：dataclass でも `==` は同じオブジェクトかどうかを比べると思っている**

- 思い込み：`@dataclass` は `__init__` を省略するための道具にすぎない
- 実際：`__eq__` と `__repr__` も自動で作る。`==` はフィールドの値で比べる
- 確かめるコード：`DMsg("a", "b") == DMsg("a", "b")` を実行する

### 理解度チェック

- **言える**：`is` と `==` は、それぞれ何を比べるか
- **説明できる**：`__eq__` を定義していないクラスで、`==` が中身を比べない理由
- **使える**：会話ログ（`role` と `content` を持つ）のリストから重複を除いて、順番を保ったまま返す関数を書く

## デフォルト引数

### 一言でいうと

デフォルト引数の値は、**`def` の行が実行されたときに1回だけ**作られる。呼び出しのたびに作られるわけではない。
だから `def f(x=[])` の `[]` は、既定値を使ったすべての呼び出しで**共有**される。

### なぜ必要か・どこで効くか

q3 のバグそのものだ。q3 では原因を「共通だから」と書いた。共通になっていることには気づけていた。足りなかったのは「**なぜ**共通になるのか」だ。
その答えが「`[]` が評価されるのは1回だけ」で、これは「名前と参照」と「ミュータブル」の組み合わせで説明できる。

### 本体

#### `def` は「関数オブジェクトを作る文」

Python では、`def` も実行される文だ。`def` の行に来たときに関数オブジェクトが作られ、関数名という名札が貼られる。
デフォルト引数の式は、**このときに評価され、結果が関数オブジェクトに保存される**。

```python
def f(x=[]):
    x.append(1)
    return x

print(f.__defaults__)   # ([],)   ← 関数オブジェクトが既定値のリストを持っている
print(f())              # [1]
print(f())              # [1, 1]  ← 同じリストに追記されている
print(f.__defaults__)   # ([1, 1],)
```

```
def の実行時に1回だけ:
  f ──→ 関数オブジェクト
          └ __defaults__ ──→ [ ]  ← このリストが、既定値を使う全呼び出しで共有される

1回目の f()：x ──→ 同じリスト → append → [1]
2回目の f()：x ──→ 同じリスト → append → [1, 1]
```

q3 のクラスに当てはめると、こうなる。

```python
class ToolAgent:
    def __init__(self, tools=[]):   # この [] は class 文の実行時に1回だけ作られる
        self.tools = tools          # a1.tools も a2.tools も、同じリストに貼られる
```

`self.tools = tools` は代入なので、コピーは作られない（`ref.assign-copies` を思い出そう）。`a1.tools` と `a2.tools` は、`__defaults__` の中の1つのリストに貼られた2枚の名札になる。

#### 正しい書き方1：既定値を `None` にする

```python
class ToolAgent:
    def __init__(self, tools=None):
        self.tools = list(tools) if tools is not None else []   # 呼ばれるたびに新しいリスト

    def add_tool(self, name):
        self.tools.append(name)
```

`[]` が関数の**本体**にあるので、呼ばれるたびに評価され、毎回新しいリストができる。
`list(tools)` でコピーしているのは、呼び出し側が渡したリストと共有しないためだ（防御的コピー）。

#### 正しい書き方2：dataclass の `default_factory`

```python
from dataclasses import dataclass, field

@dataclass
class ToolAgent:
    tools: list[str] = field(default_factory=list)   # インスタンスを作るたびに list() を呼ぶ
```

ちなみに `tools: list[str] = []` と書くと、dataclass はエラーにして止めてくれる。この罠がそれだけよくあるからだ。

#### ミュータブル以外でも起きる：「評価は1回」の別の顔

この罠は、リストに限らない。「評価が1回だけ」という性質は、時刻などでも問題になる。

```python
import time

def log(msg, at=time.time()):   # 時刻は def の実行時に1回だけ決まる
    print(at, msg)

log("a")
time.sleep(1)
log("b")    # "a" と同じ時刻が出る
```

### よくある誤解

**`def.fresh-per-call`：デフォルト引数の `[]` は、呼び出すたびに新しく作られると思っている**

- 思い込み：既定値は、引数を省略して呼んだときにその場で作られる
- 実際：`def` の実行時に1回だけ作られ、関数オブジェクトの `__defaults__` に保存される
- 確かめるコード：`print(関数名.__defaults__)` を、呼び出しの前と後で比べる

### 理解度チェック

- **言える**：デフォルト引数の値が作られるのはいつか
- **説明できる**：`def f(x=[])` が危ない理由を、「名前と参照」「ミュータブル」という2つの言葉を使って説明する
- **使える**：次の関数を、呼び出しごとに独立した結果を返すように直す

  ```python
  def build_messages(user_text, history={"turns": []}):
      history["turns"].append(user_text)
      return history
  ```

## 入口の問題をもう一度

### q3：`tools=[]` のバグ

> 原因：`tools=[]` の `[]` は、`__init__` を定義した（`def` を実行した）ときに1回だけ作られる。既定値を使って作った `a1` と `a2` は、`self.tools = tools` で同じリストに名札を貼る。代入はコピーしないので、`a1` から `append` すると `a2` からも見える。

最初の回答「共通だから」は、この説明の最後の結果だけを言っていた。
「なぜ共通か」を説明するには、**評価のタイミング**（デフォルト引数）、**代入はコピーしない**（名前と参照）、**`append` は中身の書き換え**（ミュータブル）の3つが要る。

### q7：`==` の比較

> `Msg` は `__eq__` を定義していないので、`==` は `object.__eq__`、つまり同一性の比較になる。2つの `Msg(...)` は別々に作ったオブジェクトなので `False`。`DMsg` は `@dataclass` がフィールドを比べる `__eq__` を作るので `True`。答えは「`False` と `True`」。

最初の答え「`True` と `True`」は、`eq.always-content`（`==` は常に中身を比べる）の思い込みから来ている。

### q1（前半）：なぜ `coder` から `planner` の記録が見えるのか

この章の知識で言えるのはここまでだ。

> `history = []` の `[]` は、`class` 文の実行時に1回だけ作られる。リストは1つしか存在しない。`planner` も `coder` も、`self.history` で結局このリストにたどり着くので、`append` の結果が両方から見える。

「`self.history` で、なぜクラスのリストにたどり着くのか」は第2章の「属性の探索」で扱う。

## 隣の概念

- **属性の探索**（第2章）：`self.x` がどこから見つかるか。q1 の後半はここで解ける
- **クラス変数**（第2章）：クラス直下に書いた変数。この章の「共有されたミュータブル」がいちばん出やすい場所
- **イミュータブルな設計**：`frozen=True` の dataclass や、タプルを使って、そもそも共有しても壊れないようにする考え方
- **ハッシュテーブル**：`set` や `dict` が `__hash__` と `__eq__` をどう使って高速に検索しているか。データ構造の基礎として、いずれ学ぶ価値がある

## 理解度チェックの答え

### 名前と参照

- **言える**：同じ1つのオブジェクトに、名札が2枚貼られている。`a is b` は `True`
- **説明できる**：箱モデルでは代入で中身がコピーされると考えるが、Python では名札が増えるだけでオブジェクトは1つ。`a = [9]` は `a` の名札を新しいオブジェクトに貼り替えるだけなので、元のオブジェクトに貼られた `b` は影響を受けない
- **使える**：`[1, 2] [1, 2, 3, 4]`。`y = y + [3]` で `y` は新しいリストに移るので、それ以降の `append` は `x` に影響しない

### ミュータブル

- **言える**：ミュータブルは `list`、`dict`。イミュータブルは `str`、`tuple`、`int`
- **説明できる**：`x += 1` は、新しい int オブジェクトを作って `x` の名札を貼り替える（元の int は変わらない）。`lst.append(1)` は、名札はそのままで、`lst` が指すリストそのものを書き換える
- **使える**：

  ```python
  def with_temperature(config, t):
      return {**config, "temperature": t}   # 新しい辞書を作って返す
  ```

### 同一性と同値性

- **言える**：`is` は同じオブジェクトかどうか、`==` は `__eq__` が決める「等しさ」を比べる
- **説明できる**：何をもって等しいとするかはクラスごとに違うので、Python は勝手に決めない。`__eq__` が無ければ、`object` から受け継いだ「同一性で比べる」`__eq__` が使われる
- **使える**：

  ```python
  def dedupe(messages):
      seen, out = set(), []
      for m in messages:
          key = (m["role"], m["content"])   # タプルはイミュータブルなので set に入れられる
          if key not in seen:
              seen.add(key)
              out.append(m)
      return out
  ```

### デフォルト引数

- **言える**：`def` の行が実行されたとき、1回だけ
- **説明できる**：`[]` は1回しか作られないので、既定値を使う呼び出しはすべて同じリストに名札を貼る（名前と参照）。そのリストを `append` で書き換えると、全員から変化が見える（ミュータブル）
- **使える**：

  ```python
  def build_messages(user_text, history=None):
      history = {"turns": []} if history is None else history
      history["turns"].append(user_text)
      return history
  ```
