## クラスとインスタンス

### 一言でいうと

**クラス**は「この種類のものは、どんなデータと操作を持つか」を決めた**設計**。**インスタンス**は、その設計から作った**1つ1つの実体**だ。
設計は1つ、実体は何個でも作れる。実体ごとに値（データ）は違うが、操作の仕方は共通だ。

### なぜ必要か・どこで効くか

q9 では、ボールペンの「ケース」をクラスに当てた。でも、ケースは手に取れる1本の実物だ。実物はインスタンスの側に入る。
この区別があいまいだと、「クラスに書いた変数は誰のものか」（q1）で迷う。クラスが設計なら、そこに書いた変数は設計に1つだけある。実体ごとにあるわけではない。

### 本体

#### q9 のボールペンを直す

q9 の例は、少し直すととても良い説明になる。

| ボールペンの話 | Python の話 |
|---|---|
| 「この型番のボールペン」という**設計** | クラス `Pen` |
| お店で買った1本1本の**実物** | インスタンス `p1 = Pen("赤")`、`p2 = Pen("黒")` |
| 1本ごとに違う**インクの色** | インスタンス変数 `self.color` |
| 買った時に**インクを入れる** | `__init__`（インスタンスを作った直後の初期化） |
| どの1本も、**ノックすると芯が出る** | メソッド `knock()` |

```python
class Pen:
    def __init__(self, color):   # インクを入れる
        self.color = color

    def knock(self):             # どの1本も同じ操作ができる
        return f"{self.color}の芯が出た"

p1 = Pen("赤")
p2 = Pen("黒")
print(p1.knock())   # 赤の芯が出た
print(p2.knock())   # 黒の芯が出た
```

「インクを入れる」を思いついたのは良い発見だった。それはまさに `__init__` だ。足りなかったのは「設計（型番）」と「実物（1本）」の区別と、全員に共通する操作（メソッド）だ。

#### 抽象と具体

クラスとインスタンスの関係は、**抽象と具体**の関係そのものだ。

- 抽象化：たくさんの具体（赤いペン、黒いペン、青いペン）から、共通の形（色を持つ・ノックできる）を抜き出す → クラス
- 具体化：共通の形に、個別の値を入れて実物を作る → インスタンス

クラスを設計するとは、「このプログラムに出てくるものの共通の形は何か」を考えることだ。

#### クラスもオブジェクト

第1章で「Python では値はすべてオブジェクト」と書いた。**クラスそのものもオブジェクト**だ。`class Pen:` を実行すると、クラスオブジェクトが作られ、`Pen` という名札が貼られる。

```python
print(type(p1))          # <class '__main__.Pen'>  ← p1 は Pen のインスタンス
print(type(Pen))         # <class 'type'>          ← Pen 自体もオブジェクト（type のインスタンス）
print(isinstance(p1, Pen))  # True
```

クラスがオブジェクトだからこそ、クラスも自分の属性（クラス変数やメソッド）を持てる。これが後で「属性の探索」の話につながる。

### よくある誤解

**`cls.object-as-class`：1つの実物（入れ物）をクラスと捉え、設計図と実体の区別が曖昧になっている**

- 思い込み：手に取れる入れ物がクラスで、そこに中身を入れたものがインスタンス
- 実際：クラスは「型番・設計」で、手に取れる1つ1つの実物がインスタンス。実物は何個でも作れる
- 確かめ方：その例で「インスタンスを2つ作る」と何に当たるかを考える。2つ作れないなら、クラスとインスタンスの当て方がずれている

### 理解度チェック

- **言える**：クラスとインスタンスの違い
- **説明できる**：身近な例で、「共通の操作」と「個別の値」の両方を入れて、クラスとインスタンスを説明する
- **使える**：`model` と `name` を持ち、`run(prompt)` で `"[name/model] prompt"` を返す `Agent` クラスを書き、別々の値を持つインスタンスを2つ作る

## self

### 一言でいうと

`self` は、メソッドの**第1引数**に入る「いま操作しているインスタンス」だ。予約語ではなく、ただの引数名にすぎない。
`a.run(x)` と書くと、Python はそれを `A.run(a, x)` に書き換えて呼ぶ。ドットの左側のインスタンスが、第1引数 `self` に入る。

### なぜ必要か・どこで効くか

q2 は正解したが、「ピンと来ない」と書いた。`self` を「おまじない」として覚えているうちは、こうなる。
仕組みとして分かると、「メソッドはただの関数」と見えるようになる。エラーメッセージの意味も読めるようになる。

### 本体

#### メソッドは「クラスに置いてある関数」

`class` の中に書いた `def` は、ただの関数だ。それがクラスオブジェクトの属性として置かれているだけだ。

```python
class Agent:
    def __init__(self, name):
        self.name = name

    def run(self, prompt):
        return f"[{self.name}] {prompt}"

a = Agent("planner")

print(Agent.run)               # <function Agent.run at ...>  ← ただの関数
print(Agent.run(a, "やあ"))     # [planner] やあ  ← 関数として、a を自分で渡して呼べる
print(a.run("やあ"))            # [planner] やあ  ← 上と同じ意味
```

`a.run("やあ")` は、`Agent.run(a, "やあ")` の**書き換え**だ。この書き換えのおかげで、毎回インスタンスを自分で渡さずに済む。

#### 束縛メソッド：`a.run` の正体

`a.run` を、呼ばずに取り出してみる。

```python
m = a.run
print(m)            # <bound method Agent.run of <Agent object ...>>
print(m("やあ"))     # [planner] やあ
```

`a.run` は「`Agent.run` という関数」と「`a` というインスタンス」をセットにしたオブジェクトだ。これを**束縛メソッド**（bound method）と呼ぶ。呼ばれると、セットにした `a` を第1引数に入れて関数を呼ぶ。

#### `self` を書き忘れたときのエラーを読む

```python
class Agent:
    def run(prompt):         # self を書き忘れた
        return prompt

Agent().run("やあ")
# TypeError: Agent.run() takes 1 positional argument but 2 were given
```

「引数を1個しか渡していないのに、2個渡されたと言われる」。仕組みが分かると、これは当然だ。`a.run("やあ")` は `Agent.run(a, "やあ")` になる。インスタンスと `"やあ"` の2個が渡されるのに、関数は `prompt` の1個しか受け取れない。

#### Java の `this` と比べると

| | Java | Python |
|---|---|---|
| いまのインスタンス | `this` | `self` |
| 書き方 | **暗黙**。引数に書かない | **明示**。第1引数に必ず書く |
| 属性へのアクセス | `name` だけでも書ける | 必ず `self.name` と書く |
| 名前 | 予約語 | ただの引数名（慣習で `self`） |

Java では `this` が暗黙に渡されるので、仕組みが見えにくい。Python は同じことを、普通の引数として**見える形**でやっている。

### よくある誤解

**`self.magic`：`self` は Python が特別扱いするキーワードで、呼び出し側から渡すものだと思っている**

- 思い込み：`self` は特別な予約語。または、呼ぶときに `a.run(self, "やあ")` と渡す
- 実際：`a.run(x)` は `A.run(a, x)` の書き換え。`self` はその第1引数に付けた名前にすぎない
- 確かめるコード：`self` を `me` に書き換えても動くことを確かめる（実務では `self` を使うこと）

### 理解度チェック

- **言える**：`a.run(x)` を「クラス.メソッド(…)」の形に書き直す
- **説明できる**：`takes 1 positional argument but 2 were given` が出る理由
- **使える**：`Agent` に `run` を2回続けて呼ぶ `run_twice(prompt)` メソッドを、`run` を再利用して書く

## 属性の探索

### 一言でいうと

`obj.x` と書くと、Python は `x` を **インスタンス → そのクラス → 親クラス（さらにその親……）** の順に探し、最初に見つかったものを使う。
ただし、**読むときと書くときで動きが違う**。読むときは上の順に探しに行く。でも `obj.x = ...` と代入すると、いつもインスタンス自身に属性を作る。

### なぜ必要か・どこで効くか

q1 で `coder.history` が `['計画を立てた']` になった理由の後半が、これだ。
q1 のメモ「別のインスタンスなんじゃないの？」はその通りで、`planner` と `coder` は別のインスタンスだ。ただ、**どちらも `history` を持っていない**。だから2人とも、同じクラスの `history` を探しに行く。

### 本体

#### `__dict__` で中身を見る

インスタンスもクラスも、自分の属性を `__dict__` という辞書に持っている。q1 のコードで確かめてみよう。

```python
class Agent:
    history = []

    def __init__(self, name):
        self.name = name

    def remember(self, text):
        self.history.append(text)

planner = Agent("planner")
coder = Agent("coder")

print(planner.__dict__)   # {'name': 'planner'}   ← history は無い！
print(coder.__dict__)     # {'name': 'coder'}     ← こちらにも無い
print("history" in Agent.__dict__)   # True       ← history はクラスにだけある
```

インスタンスが持っているのは、`__init__` で `self.name = ...` と代入した `name` だけだ。`history` はクラスの `__dict__` に1つあるだけで、インスタンスを作ってもコピーされない。

#### 読むときの探索

```
planner.history を読む

  ① planner.__dict__ に history はある？ → 無い
  ② Agent.__dict__ に history はある？   → ある！ これを使う

coder.history を読む

  ① coder.__dict__ に history はある？   → 無い
  ② Agent.__dict__ に history はある？   → ある！ これを使う（planner と同じリスト）
```

```
planner ──→ { name: 'planner' }
               │ history が無い → クラスへ
               ▼
Agent ──→ { history: ──→ [ '計画を立てた' ] ,  remember: ..., __init__: ... }
               ▲
               │ history が無い → クラスへ
coder ──→ { name: 'coder' }
```

メソッドもこの仕組みで見つかる。`planner.remember` も、`planner.__dict__` には無いので、`Agent.__dict__` から見つかる。**メソッドとクラス変数は、同じ仕組みで探されている**。

#### 書くときは、いつもインスタンスに作る

ここが落とし穴だ。代入は探索をしない。

```python
class Counter:
    count = 0                 # クラス変数（int、イミュータブル）

    def up(self):
        self.count += 1       # self.count = self.count + 1 と同じ

c1 = Counter()
c2 = Counter()
c1.up()

print(c1.count, c2.count)     # 1 0
print(c1.__dict__)            # {'count': 1}   ← インスタンスに新しく作られた
print(Counter.count)          # 0              ← クラスの count は変わっていない
```

`self.count += 1` は、こう動く。

1. 右辺の `self.count` を**読む**：インスタンスに無いので、クラスの `0` が見つかる
2. `0 + 1` で新しい int オブジェクト `1` ができる
3. `self.count = 1` と**書く**：書き込みはいつもインスタンスへ。`c1.__dict__` に `count` が作られる

以後、`c1.count` はインスタンスの `count` が先に見つかるので、クラスの `count` は隠れる。

#### q1 と Counter の違い

| | q1 の `history` | Counter の `count` |
|---|---|---|
| 操作 | `self.history.append(...)` | `self.count += 1` |
| `self.xxx` を | **読んで**、その先のリストを書き換える | **読んで**、結果を**代入**する |
| インスタンスに属性ができるか | できない | できる |
| 結果 | 全員で1つのリストを共有し、変化が全員に見える | `c1` だけが自分の `count` を持つ |

q1 の `self.history.append(...)` には代入（`self.history = ...`）が無い。だからずっとクラスのリストを触り続ける。
第1章の「名札の貼り替え（rebind）」と「中身の書き換え（mutate）」の区別が、ここでも効いている。

### よくある誤解

**`attr.copied-on-create`：インスタンスを作るとき、クラスに書いた変数がインスタンスごとにコピーされると思っている**

- 思い込み：`Agent("coder")` を作ると、`history = []` が `coder` 用にもう1つ作られる
- 実際：コピーはされない。インスタンスに無い属性は、読むたびにクラスへ探しに行く
- 確かめるコード：`print(coder.__dict__)` に `history` が無いことを見る

**`attr.read-write-same`：`self.x` を読むことと `self.x` に代入することが、同じ場所を触ると思っている**

- 思い込み：`self.count += 1` は、クラスの `count` を増やす
- 実際：読むときはクラスまで探すが、代入はいつもインスタンスに新しい属性を作る
- 確かめるコード：上の Counter を実行し、`c1.__dict__` と `Counter.count` を見る

### 理解度チェック

- **言える**：`obj.x` を読むとき、Python が `x` を探す順番
- **説明できる**：`self.x` を読むときと、`self.x = ...` と書くときで、何が違うか
- **使える**：次のコードの出力を予測する

  ```python
  class A:
      tags = []
      level = 1

  a, b = A(), A()
  a.tags.append("x")
  a.level = 5
  print(b.tags, b.level, A.level)
  ```

## クラス変数

### 一言でいうと

クラス直下に書いた変数。**クラスに1つだけ**あり、全インスタンスから（属性の探索を通して）見える。
Java や C# の `static` フィールドに近い。

### なぜ必要か・どこで効くか

q1 のメモ「これstaticなのか？」への答えがこの節だ。ほぼその通りだが、Python には Java に無いクセがある。そこを押さえないと、またq1のようなバグを作る。

### 本体

#### インスタンス変数とクラス変数

```python
class Agent:
    default_model = "claude-sonnet-5-5"   # クラス変数：クラスに1つ

    def __init__(self, name, model=None):
        self.name = name                   # インスタンス変数：インスタンスごと
        self.model = model or Agent.default_model
```

| | インスタンス変数 | クラス変数 |
|---|---|---|
| 書く場所 | メソッドの中で `self.x = ...`（主に `__init__`） | クラス直下に `x = ...` |
| どこにあるか | インスタンスの `__dict__` | クラスの `__dict__` |
| 何個あるか | インスタンスの数だけ | 1つだけ |
| 向いている用途 | 名前、会話履歴、設定など、個体ごとに違うもの | 定数、全体で共有するカウンタ、既定値（イミュータブルなもの） |

#### Java の `static` と比べると

```java
// Java
class Agent {
    static List<String> history = new ArrayList<>();   // 全インスタンスで共有
}
```

```python
# Python
class Agent:
    history = []                                       # 全インスタンスで共有
```

| | Java の `static` | Python のクラス変数 |
|---|---|---|
| 個数 | クラスに1つ | クラスに1つ |
| インスタンスから読む | `this.history` で読めるが、警告が出る書き方 | `self.history` で普通に読める（属性の探索） |
| インスタンスから代入 | クラスの `static` が書き換わる | **インスタンスに同名の属性ができて、クラス変数を隠す** |
| 見た目 | `static` が付くので一目で分かる | 何も付かない。**クラス直下に書いただけ**でクラス変数になる |

一番の違いは最後の2行だ。

- Python には `static` のような目印が無い。クラス直下に `history = []` と書いただけで、クラス変数になる。インスタンス変数のつもりで書いてしまいやすい
- インスタンスから代入すると、Java ではクラスの値が変わるが、Python ではインスタンスに新しい属性ができる（前の節の Counter）

#### クラス変数を正しく使う

```python
class Agent:
    MAX_TURNS = 20               # 定数：イミュータブルなので共有しても安全
    created = 0                  # 全体のカウンタ

    def __init__(self, name):
        self.name = name
        self.history = []        # インスタンスごとのリストは、必ず __init__ で作る
        Agent.created += 1       # クラス変数を書き換えるときは、クラス名で書く
```

- インスタンスごとに持つべきミュータブルな値（リスト、辞書）は、**必ず `__init__` で `self.x = ...` と作る**
- クラス変数を書き換えるときは `self.created` ではなく **`Agent.created`** と書く。`self.created += 1` と書くと、インスタンスに属性ができてしまう

### よくある誤解

**`cls.var-per-instance`：クラス直下に書いた変数も、インスタンスごとに別々に持たれると思っている**

- 思い込み：`history = []` をクラスに書けば、インスタンスごとに履歴を持てる
- 実際：クラス直下の変数はクラスに1つだけ。インスタンスごとに持たせたいなら `__init__` で `self.history = []` と書く
- 確かめるコード：`planner.history is coder.history` が `True` になることを見る

### 理解度チェック

- **言える**：クラス変数とインスタンス変数の、書く場所の違い
- **説明できる**：ミュータブルなクラス変数が全インスタンスで共有される仕組みを、「属性の探索」と「ミュータブル」の2つの言葉で説明する
- **使える**：q1 の `Agent` を、インスタンスごとに履歴を持つように直す。さらに、作られたエージェントの総数を数えるクラス変数を足す

## 継承

### 一言でいうと

`class Child(Parent):` と書くと、属性の探索の行き先に**親クラスが加わる**。子クラスのインスタンスで見つからない属性は、子クラス → 親クラス の順に探される。
子クラスで同じ名前の属性を定義すると、探索で先に見つかるので、親のものは隠れる。これが**オーバーライド**（上書き）だ。

### なぜ必要か・どこで効くか

q4 のメモに「Pythonの継承関係はほぼ初学状態」とあった。継承を「親のコードを子にコピーする機能」と捉えていると、オーバーライドしたときに何が消えるのかが見えない。
継承を「探索の行き先が増えるだけ」と捉えると、q4 は前の節の知識だけで解ける。

### 本体

#### 探索の行き先が増える

```python
class Agent:
    def __init__(self, name):
        self.name = name

    def run(self, prompt):
        return f"[{self.name}] {prompt}"

    def describe(self):
        return f"Agent {self.name}"

class LoggingAgent(Agent):          # Agent を継承
    def run(self, prompt):          # run をオーバーライド
        print("LOG:", prompt)
        return f"[{self.name}] {prompt}"

la = LoggingAgent("planner")
la.run("やあ")        # LoggingAgent.run が見つかる
la.describe()         # LoggingAgent に無い → Agent.describe が見つかる
```

```
la.describe を読む

  ① la.__dict__            → 無い（name だけ）
  ② LoggingAgent.__dict__  → 無い（run だけ）
  ③ Agent.__dict__         → ある！ これを使う

la.run を読む

  ① la.__dict__            → 無い
  ② LoggingAgent.__dict__  → ある！ これを使う（Agent.run には行かない）
```

探す順番は `クラス名.__mro__`（Method Resolution Order、メソッド解決順序）で確かめられる。

```python
print(LoggingAgent.__mro__)
# (<class 'LoggingAgent'>, <class 'Agent'>, <class 'object'>)
```

最後の `object` は、すべてのクラスの祖先だ。第1章の「`__eq__` を書かないと `object.__eq__` が使われる」も、この探索の結果だ。

#### コピーではない証拠

継承がコピーなら、継承した後に親を変えても子には影響しないはずだ。実際は影響する。

```python
Agent.greet = lambda self: f"こんにちは、{self.name}です"   # 後から親にメソッドを足す
print(la.greet())    # こんにちは、plannerです  ← 子のインスタンスからも使える
```

子は親のコードを持っていない。見つからなければ、そのつど親を探しに行っている。

#### 「is-a」の関係

継承は「子は親の一種である（is-a）」と言えるときに使う。`LoggingAgent` は `Agent` の一種なので、`Agent` を受け取る場所に `LoggingAgent` を渡しても困らない。

```python
print(isinstance(la, Agent))   # True
```

「一種である」と言えないのに、コードを使い回したいだけで継承すると、設計が苦しくなる。これは第3章の「継承と合成」で扱う。

### よくある誤解

**`inh.code-copied`：継承すると、親クラスのコードが子クラスにコピーされると思っている**

- 思い込み：`class Child(Parent):` で、親のメソッドが子の中に複製される
- 実際：コピーではなく、見つからなかったら親を探しに行く仕組み。だから親を後から変えると子にも反映される
- 確かめるコード：`print(LoggingAgent.__dict__.keys())` に `describe` が無いことを見る

### 理解度チェック

- **言える**：オーバーライドとは何か
- **説明できる**：子クラスのインスタンスで親のメソッドが呼べる理由を、「属性の探索」の言葉で説明する
- **使える**：`Agent` を継承し、`run` の結果の末尾に `"（要約済み）"` を付ける `SummaryAgent` を書く

## super

### 一言でいうと

`super()` は、**MRO で自分の次にあるクラス**のメソッドを呼ぶための道具だ。
子クラスで `__init__` を定義すると、それが親の `__init__` をオーバーライドする。だから**親の `__init__` は自動では呼ばれない**。親の初期化が必要なら、`super().__init__(...)` を自分で呼ぶ。

### なぜ必要か・どこで効くか

q4 がこれだ。答えは `AttributeError` だったが、`TypeError`（引数の数が合わない）を選んだ。
「子と親で `__init__` の引数が違うから、エラーになる」と考えたのだと思う。でも、呼ばれるのは子の `__init__` だけなので、引数の数は子の定義と合っていればよい。問題は「親の `__init__` が一度も呼ばれない」ことだ。

### 本体

#### q4 を属性の探索で読む

```python
class Agent:
    def __init__(self, model):
        self.model = model

class RetryAgent(Agent):
    def __init__(self, model, max_retry):   # Agent.__init__ をオーバーライド
        self.max_retry = max_retry

    def info(self):
        return f"{self.model} x{self.max_retry}"

r = RetryAgent("claude-sonnet-5-5", 3)
```

1. `RetryAgent("claude-sonnet-5-5", 3)` で、Python はインスタンスを作り、`__init__` を**探す**
2. `RetryAgent.__dict__` に `__init__` がある → それを呼ぶ。`Agent.__init__` までは探しに行かない
3. 引数は `self, model, max_retry` の3つ。渡したのもインスタンスと2つの値。**数は合っている**（だから `TypeError` にはならない）
4. 実行されるのは `self.max_retry = max_retry` だけ。`self.model = model` は一度も実行されない
5. `r.info()` で `self.model` を読む → インスタンスにもクラスにも親にも `model` が無い → **`AttributeError`**

```python
print(r.__dict__)   # {'max_retry': 3}  ← model が無い
```

#### `super().__init__` で直す

```python
class RetryAgent(Agent):
    def __init__(self, model, max_retry):
        super().__init__(model)      # 親の初期化を、まず実行する
        self.max_retry = max_retry   # そのあと、子で足したい属性を作る

r = RetryAgent("claude-sonnet-5-5", 3)
print(r.__dict__)   # {'model': 'claude-sonnet-5-5', 'max_retry': 3}
print(r.info())     # claude-sonnet-5-5 x3
```

`__init__` 以外のメソッドでも同じだ。オーバーライドしたメソッドの中から親の処理を使いたいときは、`super().メソッド名(...)` と書く。

```python
class LoggingAgent(Agent):
    def run(self, prompt):
        print("LOG:", prompt)
        return super().run(prompt)   # 親の run に任せる（コードを複製しない）
```

#### なぜ `Agent.__init__(self, model)` ではなく `super()` なのか

`Agent.__init__(self, model)` と書いても、単純な継承なら動く。でも `super()` が推奨される理由が2つある。

1. 親クラスの名前を変えたり、間に別のクラスを挟んだりしても、書き直さずに済む
2. 複数の親を持つ継承（多重継承）では、`super()` が MRO の順に親をたどってくれる。各クラスの `__init__` が一度ずつ、正しい順で呼ばれる

```python
class Base:
    def __init__(self):
        print("Base")

class WithLog(Base):
    def __init__(self):
        print("WithLog"); super().__init__()

class WithRetry(Base):
    def __init__(self):
        print("WithRetry"); super().__init__()

class Client(WithLog, WithRetry):
    def __init__(self):
        print("Client"); super().__init__()

Client()
# Client → WithLog → WithRetry → Base の順に1回ずつ表示される
print(Client.__mro__)
```

`super()` は「親」ではなく、「**MRO で次のクラス**」を呼ぶ。`WithLog` の中の `super()` が、`WithLog` の親の `Base` ではなく `WithRetry` を呼んでいることに注目しよう。
多重継承は難しいので、実務ではなるべく避ける（第3章の「合成」を使う）。ここでは「`super()` は MRO をたどる」とだけ覚えておけばよい。

#### dataclass を継承するとき

`@dataclass` は `__init__` を自動で作る。親も子も dataclass なら、子の `__init__` は親のフィールドも含めて自動で作られるので、`super().__init__` を書く必要はない。
自分で `__init__` を書いたときだけ、`super()` のことを考えればよい。

### よくある誤解

**`super.auto-init`：子クラスで `__init__` を書いても、親の `__init__` も自動で実行されると思っている**

- 思い込み：子のインスタンスを作れば、親の `__init__` → 子の `__init__` の順に両方呼ばれる
- 実際：子の `__init__` が親の `__init__` を上書きする。親の初期化が必要なら `super().__init__(...)` を自分で呼ぶ
- 確かめるコード：親の `__init__` に `print("親")` を入れ、子のインスタンスを作って表示されないことを見る

**`super.signature-error`：子と親で `__init__` の引数の数が違うと、それだけで `TypeError` になると思っている**

- 思い込み：子の `__init__(self, model, max_retry)` と親の `__init__(self, model)` が食い違うのでエラーになる
- 実際：呼ばれるのは子の `__init__` だけなので、引数の数は子の定義と合っていればよい。問題は親の初期化が抜けること
- 確かめるコード：q4 のコードで `print(r.__dict__)` を実行し、エラーにならずに `{'max_retry': 3}` が出ることを見る

### 理解度チェック

- **言える**：子で `__init__` を定義したとき、親の `__init__` は呼ばれるか
- **説明できる**：`super().__init__(...)` を書き忘れると何が起きるか。エラーが出るのが「インスタンスを作るとき」ではなく「`self.model` を読むとき」なのはなぜか
- **使える**：`Agent(name, model)` を継承し、`temperature` を追加で受け取る `TunedAgent` を、親の初期化を活かして書く

## 入口の問題をもう一度

### q1：なぜ `coder` から `planner` の記録が見えるのか

> `history = []` はクラス直下にあるのでクラス変数で、リストは `Agent.__dict__` に1つだけある（第1章：`[]` は1回しか評価されない）。インスタンスを作ってもコピーされない（`attr.copied-on-create` の否定）。`planner.remember(...)` の中の `self.history` は、インスタンスに `history` が無いのでクラスのリストにたどり着き、`append` で中身を書き換える（代入ではないので、インスタンスに属性はできない）。`coder.history` も同じリストにたどり着くので、`['計画を立てた']` が見える。

メモの「これstaticなのか？」には、こう答えられる。**ほぼ static。ただし Python には `static` の目印が無く、クラス直下に書いただけでそうなる。** 直し方は `__init__` で `self.history = []` と書くことだ。

### q2：`planner.remember("計画を立てた")` の正体

> `planner.remember` は、`planner.__dict__` に無いので `Agent.__dict__` から関数 `remember` が見つかる。インスタンスから取り出したので、`planner` とセットになった束縛メソッドになる。呼ぶと `planner` が第1引数 `self` に入る。つまり `Agent.remember(planner, "計画を立てた")`。

「属性の探索」と「self」がつながると、q2 の答えは暗記ではなく、仕組みから導けるようになる。

### q4：子クラスの `__init__`

> 子の `__init__` が親の `__init__` をオーバーライドするので、`self.model = model` は実行されない。引数の数は子の定義と合っているので `TypeError` にはならない。`info()` で `self.model` を読むと、どこにも `model` が無いので `AttributeError`。

最初の答え `TypeError` は、`super.signature-error` の思い込みから来ている。

### q9：クラスとインスタンスの説明

> 「この型番のボールペン」という設計がクラス。買ってきた1本1本がインスタンス。どの1本もノックすれば芯が出る（共通の操作＝メソッド）けれど、入れたインクの色は1本ごとに違う（個別の値＝インスタンス変数）。インクを入れるのは、買った直後の準備（`__init__`）に当たる。

## 隣の概念

- **ダックタイピング**（第3章）：継承していなくても、同じメソッドを持っていれば同じように扱える。「探索して見つかればよい」という、この章の仕組みの延長にある
- **継承と合成**（第3章）：継承は is-a のときだけ。機能を足したいだけなら、包む（合成する）方がよいことが多い
- **抽象基底クラス（ABC）**：「子クラスは必ずこのメソッドを実装すること」を強制する仕組み。Java の抽象クラスに当たる
- **classmethod / staticmethod**：インスタンスではなくクラスを第1引数に受け取るメソッドと、何も受け取らないメソッド。Java の static メソッドに近いのは staticmethod

## 理解度チェックの答え

### クラスとインスタンス

- **言える**：クラスはデータと操作の形を決めた設計、インスタンスはそこから作った個々の実体
- **説明できる**：例）社員証。書式（名前・所属の欄と、ゲートにかざすと開く機能）がクラス、一人一人の社員証がインスタンス。欄の中身は人ごとに違うが、ゲートを開ける働きは全員共通
- **使える**：

  ```python
  class Agent:
      def __init__(self, name, model):
          self.name = name
          self.model = model

      def run(self, prompt):
          return f"[{self.name}/{self.model}] {prompt}"

  a = Agent("planner", "claude-opus-5-5")
  b = Agent("coder", "claude-sonnet-5-5")
  ```

### self

- **言える**：`A.run(a, x)`
- **説明できる**：`a.run("やあ")` は `A.run(a, "やあ")` に書き換えられ、インスタンスと `"やあ"` の2つが渡される。`self` を書き忘れた関数は1つしか受け取れないので、数が合わない
- **使える**：

  ```python
  def run_twice(self, prompt):
      return [self.run(prompt), self.run(prompt)]
  ```

### 属性の探索

- **言える**：インスタンス → クラス → 親クラス（MRO の順）
- **説明できる**：読むときは見つかるまで上へ探しに行く。代入はいつもインスタンス自身に属性を作る（クラスの属性は変わらない）
- **使える**：`['x'] 1 1`。`a.tags.append` はクラスの共有リストを書き換えるので `b` からも見える。`a.level = 5` は `a` にだけ属性を作るので、`b.level` と `A.level` は `1` のまま

### クラス変数

- **言える**：クラス変数はクラス直下、インスタンス変数はメソッドの中で `self.x = ...`
- **説明できる**：インスタンスに無い属性は読むときにクラスへ探しに行く（属性の探索）ので、全インスタンスがクラスの1つのリストにたどり着く。それを `append` で書き換えると（ミュータブル）、全員から変化が見える
- **使える**：

  ```python
  class Agent:
      created = 0

      def __init__(self, name):
          self.name = name
          self.history = []
          Agent.created += 1

      def remember(self, text):
          self.history.append(text)
  ```

### 継承

- **言える**：子クラスで親と同じ名前の属性を定義し、探索で先に見つかるようにして、親のものを隠すこと
- **説明できる**：子のインスタンスで見つからない属性は、子クラス → 親クラスの順に探される。子クラスに無いメソッドは、親クラスで見つかる
- **使える**：

  ```python
  class SummaryAgent(Agent):
      def run(self, prompt):
          return super().run(prompt) + "（要約済み）"
  ```

### super

- **言える**：呼ばれない
- **説明できる**：親の `__init__` が実行されないので、親が作るはずの属性が無いままになる。インスタンスを作る時点では、子の `__init__` が問題なく動くのでエラーにならない。存在しない属性を読んだ時点で、初めて `AttributeError` になる
- **使える**：

  ```python
  class TunedAgent(Agent):
      def __init__(self, name, model, temperature):
          super().__init__(name, model)
          self.temperature = temperature
  ```
