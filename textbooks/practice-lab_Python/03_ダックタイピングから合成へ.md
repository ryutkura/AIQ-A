## 基本構文

### 一言でいうと

`pass` は「**何もしない**」文だ。Python ではブロック（`class` や `def` や `if` の中身）を空にできないので、空にしたいときの穴埋めに使う。値を返す `return` とはまったく別のものだ。

### なぜ必要か・どこで効くか

q5 の `EchoClient` は、本体が `pass` だけのクラスだ。`pass` の意味が分からないと、`EchoClient` が何を持っているクラスなのかが読めない。
答えは「**自分では何も足していない。親から受け継いだものだけを持つクラス**」だ。

### 本体

#### ブロックは空にできない

Python はインデントでブロックを表す。`:` の次の行には、インデントされた文が少なくとも1つ必要だ。

```python
class EchoClient(ClaudeClient):
    # 何も書かないと IndentationError になる
```

```python
class EchoClient(ClaudeClient):
    pass      # 「何もしない」文を置いて、ブロックを成立させる
```

`pass` は実行されても何も起きない。`EchoClient` は自分では何も定義していないので、第2章の属性の探索により、`generate` を探すと `ClaudeClient.generate` が見つかる。

#### `pass`、`return`、`...` の違い

| 書き方 | 意味 | どこで使うか |
|---|---|---|
| `pass` | 何もしない。次の文へ進む | どのブロックでも使える穴埋め |
| `return` | 関数を抜けて、呼び出し元に値を返す（値を書かなければ `None`） | 関数の中だけ |
| `...`（Ellipsis） | `...` という値を書いただけの式。結果として何もしない | 「あとで書く」印として、型定義や Protocol でよく使う |

関数で何も `return` しなければ、関数は自動で `None` を返す。だから「`pass` だけの関数」は、何もせず `None` を返す関数になる。

```python
def todo():
    pass

print(todo())   # None
```

#### 本体の穴埋めに使える他のもの

ドキュメント文字列（docstring）も文なので、それだけでブロックは成立する。

```python
class EchoClient(ClaudeClient):
    """ClaudeClient と同じ振る舞いをする、名前だけ別のクライアント"""
```

### よくある誤解

**`syntax.pass-is-return`：`pass` は `return` と同じく、値を返して処理を抜ける文だと思っている**

- 思い込み：`pass` を書くと、そこで何かが返される
- 実際：`pass` は「何もしない」文。中身を空にできない場所の穴埋めに使う。値は返さない
- 確かめるコード：`if True: pass` の後に `print("続く")` を書き、処理が続くことを見る

### 理解度チェック

- **言える**：`pass` と `return` の違い
- **説明できる**：なぜ Python には `pass` が必要なのか
- **使える**：あとで実装する予定の `Planner` クラスと、その `plan(goal)` メソッドを、エラーにならない形で先に書いておく

## ダックタイピング

### 一言でいうと

Python は、オブジェクトの型や継承関係を確かめずに、**呼ばれたメソッドをその場で探す**。見つかれば動き、見つからなければ `AttributeError` になる。
だから、**継承していなくても、同じ名前のメソッドを持っていれば、同じように扱える**。

> 「アヒルのように歩き、アヒルのように鳴くなら、それはアヒルだ」

これがダックタイピングという名前の由来だ。

### なぜ必要か・どこで効くか

LLMアプリで本当によく使う。

- テストで、本物のAPIを呼ぶ `ClaudeClient` の代わりに、決まった文字列を返す `FakeLLM` を差し込む
- Claude と OpenAI を、呼び出し側のコードを変えずに切り替える
- ツール、リトライ、キャッシュなどの部品を、同じ形にそろえて組み合わせる（この章の最後の「合成」）

どれも「継承関係を作らなくても、同じメソッドを持てば差し替えられる」ことに頼っている。

### 本体

#### q5 を属性の探索で読む

```python
def ask(llm, prompt):
    return llm.generate(prompt)
```

`ask` は `llm` の型を確かめていない。やっているのは `llm.generate` を**探して呼ぶ**ことだけだ。第2章の属性の探索がそのまま働く。

| 渡したもの | `generate` の探索 | 結果 |
|---|---|---|
| `ClaudeClient()` | インスタンス → `ClaudeClient` で**見つかる** | 動く |
| `FakeLLM()` | インスタンス → `FakeLLM` で**見つかる** | 動く |
| `EchoClient()` | インスタンス → `EchoClient`（`pass` なので無い）→ 親の `ClaudeClient` で**見つかる** | 動く |
| `OldClient()` | インスタンス → `OldClient`（`complete` しか無い）→ `object` にも無い | `AttributeError` |

`ClaudeClient` も `FakeLLM` も、何も継承していない。でも `generate` を持っているので動く。継承は「探索の行き先を増やす」ための仕組みで、`ask` が動くかどうかには関係ない。

#### Java のインターフェースと比べると

Java で `ask` を書くと、こうなる。

```java
interface LLM {
    String generate(String prompt);
}

String ask(LLM llm, String prompt) {
    return llm.generate(prompt);
}

class FakeLLM implements LLM { ... }   // implements LLM と宣言しないと ask に渡せない
```

| | Java | Python |
|---|---|---|
| 「渡せるか」を決めるもの | `implements LLM` と**宣言**したか（名前で判断） | `generate` を**持っている**か（形で判断） |
| チェックのタイミング | コンパイル時 | 呼び出した瞬間（実行時） |
| 宣言を忘れたら | `generate` を持っていてもコンパイルエラー | そもそも宣言が要らない |

Java の考え方では、q5 は「`LLM` を実装していると宣言しているのはどれか」という問題になる。Python では「`generate` を持っているのはどれか」という問題になる。

#### 約束を書いておく：`typing.Protocol`

ダックタイピングは自由だが、「`generate` を持っていること」という約束がコードのどこにも書かれていない。型ヒントでそれを明示するのが `Protocol` だ。

```python
from typing import Protocol

class LLM(Protocol):
    def generate(self, prompt: str) -> str: ...

def ask(llm: LLM, prompt: str) -> str:
    return llm.generate(prompt)
```

`FakeLLM` は `LLM` を継承する必要がない。`generate(self, prompt: str) -> str` を持っていれば、mypy などの型チェッカーが「`LLM` の約束を満たしている」と判定する。
これは**構造的部分型**（形が合っていればよい）と呼ばれ、Java の**名前的部分型**（宣言した名前で判断する）と対になる。実行時の動きは、`Protocol` を書いても書かなくても変わらない。

#### ポリモーフィズム：同じ呼び出しで、違う振る舞い

同じ `llm.generate(prompt)` という呼び出しが、渡したオブジェクトによって違う動きをする。これを**ポリモーフィズム**（多態性）と呼ぶ。
ポリモーフィズムを使わないと、型ごとの分岐が呼び出し側に増えていく。

```python
# ポリモーフィズムを使わない書き方：新しいクライアントが増えるたびに、ここを直す
def ask(llm, prompt):
    if isinstance(llm, ClaudeClient):
        return llm.call_claude(prompt)
    elif isinstance(llm, OpenAIClient):
        return llm.call_openai(prompt)
    elif isinstance(llm, FakeLLM):
        return "fake"

# ポリモーフィズムを使う書き方：全員が generate を持てば、ask は二度と直さなくてよい
def ask(llm, prompt):
    return llm.generate(prompt)
```

#### テストに効く：依存性の注入

`ask` のように「使う相手を外から受け取る」書き方を、**依存性の注入**（Dependency Injection）と呼ぶ。相手を受け取るので、テストでは偽物を渡せる。

```python
class FakeLLM:
    def __init__(self, reply):
        self.reply = reply
        self.prompts = []          # 何を聞かれたかを記録しておく

    def generate(self, prompt):
        self.prompts.append(prompt)
        return self.reply

def test_ask():
    fake = FakeLLM("こんにちは")
    assert ask(fake, "挨拶して") == "こんにちは"
    assert fake.prompts == ["挨拶して"]
```

API キーもネットワークも要らず、一瞬で、毎回同じ結果になるテストが書ける。

### よくある誤解

**`duck.needs-inheritance`：共通の親クラスを継承していないと、同じ関数に渡して同じように扱えないと思っている**

- 思い込み：`ask` に渡せるのは、`ClaudeClient` の仲間（継承関係にあるクラス）だけ
- 実際：Python は呼び出したメソッドがあるかだけを見る。継承は必要ない
- 確かめるコード：何も継承しない `class Duck: def generate(self, p): return "ガー"` を作り、`ask(Duck(), "x")` を実行する

### 理解度チェック

- **言える**：ダックタイピングとは何か
- **説明できる**：何も継承していない `FakeLLM` が `ask` に渡せる理由を、第2章の「属性の探索」の言葉で説明する
- **使える**：`summarize(llm, text)` という関数と、そのテスト用の `FakeLLM` を書く。テストでは、`FakeLLM` に渡されたプロンプトに `text` が含まれていることも確かめる

## property

### 一言でいうと

`@property` を使うと、**`obj.x` という属性の書き方のまま**、読み書きのたびに処理（検証、変換、計算）を挟める。
肝は「検証できること」ではない。**呼び出し側のコードを1行も変えずに、あとから中身の実装を差し替えられること**だ。

### なぜ必要か・どこで効くか

q6 では「不正な値の入出力を許容しなくなる」と答えた。検証できるのはその通りだ。でも、検証だけなら `set_temperature(5)` というメソッドでもできる。
`property` ならではの価値は、**最初は普通の属性で書いておき、必要になってから検証を足せる**ことだ。そのとき、呼び出し側の `client.temperature = 5` は書き換えなくてよい。

### 本体

#### Java のゲッター・セッターと比べると

Java では、最初からゲッターとセッターを書くのが定石だ。

```java
class Client {
    private double temperature;
    public double getTemperature() { return temperature; }
    public void setTemperature(double t) { temperature = t; }   // 今は検証しないが、将来のために
}

client.setTemperature(5);
```

なぜ最初から書くのか。もし `public double temperature;` で公開しておいて、後から検証を足したくなったらどうなるか。`client.temperature = 5` を `client.setTemperature(5)` に、**呼び出し側を全部書き換える**ことになる。それを避けるために、Java では使うかどうか分からないゲッター・セッターを最初から書く。

Python では、この心配が要らない。

```python
# 最初：普通の属性。ゲッターもセッターも書かない
class Client:
    def __init__(self, temperature=1.0):
        self.temperature = temperature

client = Client()
client.temperature = 0.7     # 呼び出し側はこう書いている
```

```python
# あとで検証が必要になった：property に差し替える
class Client:
    def __init__(self, temperature=1.0):
        self.temperature = temperature        # ここでも下の setter が呼ばれる

    @property
    def temperature(self):                    # 読むときに呼ばれる
        return self._temperature

    @temperature.setter
    def temperature(self, value):             # 代入するときに呼ばれる
        if not 0 <= value <= 2:
            raise ValueError("temperature は 0〜2")
        self._temperature = value

client = Client()
client.temperature = 0.7     # 呼び出し側は1文字も変わっていない
client.temperature = 5       # ValueError
```

**外から見える使い方（インターフェース）を変えずに、中身（実装）を変えられた。** これが q6 の答えの核心だ。

#### property も属性の探索で見つかる

`client.temperature` を読むと、Python は属性の探索で `temperature` を探す。クラスに property が見つかると、値を返す代わりに、property に登録された関数（ゲッター）を呼ぶ。代入するときも同様にセッターが呼ばれる。
（この「探索で見つかったものが、自分の読み書きの方法を決める」仕組みを**ディスクリプタ**と呼ぶ。メソッドが束縛メソッドになるのも、実は同じ仕組みだ。）

#### 落とし穴：無限再帰

値の実体を、property と同じ名前に入れてはいけない。

```python
@temperature.setter
def temperature(self, value):
    self.temperature = value   # これがまた setter を呼ぶ → 無限に繰り返して RecursionError
```

だから実体は `self._temperature` のように別の名前に入れる。

#### 読み取り専用と、計算で求める属性

セッターを書かなければ、読み取り専用になる。値を保存せず、読むたびに計算することもできる。

```python
class Conversation:
    def __init__(self):
        self.messages = []

    @property
    def turns(self):                 # 保存していない。読むたびに数える
        return sum(1 for m in self.messages if m["role"] == "user")

c = Conversation()
c.messages.append({"role": "user", "content": "やあ"})
print(c.turns)    # 1
c.turns = 3       # AttributeError（セッターが無いので代入できない）
```

#### カプセル化：約束と実装を分ける

property の例でやったことを一般化すると、**カプセル化**になる。外に見せる約束（インターフェース）と、内部の実装を分け、実装を自由に変えられるようにすることだ。

Python のカプセル化は、Java の `private` のような強制ではなく、**名前の約束**で行う。

| 書き方 | 意味 | 外から触れるか |
|---|---|---|
| `x` | 公開。使ってよい | 触れる |
| `_x` | 内部用。外から触らないでね、という慣習 | 触れる（触らないのがマナー） |
| `__x` | 名前修飾。`_クラス名__x` という名前に変わる | `obj._クラス名__x` で触れる |

```python
class Client:
    def __init__(self):
        self._temperature = 1.0
        self.__secret = "abc"

c = Client()
print(c._temperature)        # 1.0（触れてしまう）
print(c._Client__secret)     # abc（名前を変えられているだけ）
```

`__x` の目的は「隠す」ことではなく、**サブクラスで同じ名前を使ったときの衝突を防ぐ**ことだ。普段の「内部用」の印には `_x` を使えばよい。
Python では「みんな大人なのだから、約束を守ろう」という考え方で設計されている。

### よくある誤解

**`prop.only-validation`：property の価値は値の検証だけで、メソッドで検証するのと変わらないと思っている**

- 思い込み：property は検証のための道具。`set_temperature()` を作るのと同じこと
- 実際：肝は、呼び出し側の書き方（`obj.x = v`）を変えずに実装を差し替えられること。検証はその使い道の1つ
- 確かめ方：普通の属性で書いたクラスを、property に書き換える。呼び出し側のコードが1行も変わらないことを確かめる

**`encap.private-enforced`：`_x` と書けば外から絶対に触れなくなると思っている**

- 思い込み：`_x` や `__x` は Java の `private` と同じ
- 実際：`_x` はただの慣習で、触ろうと思えば触れる。Python のカプセル化は約束で成り立つ
- 確かめるコード：上の `c._temperature` と `c._Client__secret` を実行する

### 理解度チェック

- **言える**：`@property` とセッターの書き方
- **説明できる**：メソッド（`set_temperature`）ではなく property にする利点を、呼び出し側のコードに触れて説明する
- **使える**：`max_tokens`（1以上の整数だけ許す）を持つ `Client` を、property で、無限再帰を起こさずに書く

## 継承と合成

### 一言でいうと

- **継承**：「A は B の**一種**である（is-a）」と言えるときに使う
- **合成**：「A は B を**持っている・使っている・包んでいる**（has-a）」ときに使う。B を属性として持つ

機能を組み合わせたいとき、継承で作るとクラスの数が組み合わせの数だけ増える。**合成なら、部品を必要な数だけ作り、重ねるだけで済む。**

### なぜ必要か・どこで効くか

q8 は空欄だった。この問題は、ダックタイピング（同じ約束を持てば差し替えられる）と、継承（何が is-a か）の両方が分かって、初めて手が出る。
ここまでの3節を読んだ今なら、組み立てられるはずだ。

### 本体

#### 継承で作ると、何が起きるか

クライアントが2種類（Claude、OpenAI）、機能が3つ（リトライ、ログ、キャッシュ）。継承で「機能つきのクライアント」を作るとする。

- 機能の付け方は、3つそれぞれ「付ける・付けない」で 2 × 2 × 2 = 8 通り
- それがクライアント2種類分なので、8 × 2 = **16 クラス**
- 機能が1つ増えると 32 クラス、クライアントが1つ増えると 24 クラス

```
ClaudeClient
├── RetryClaudeClient
├── LoggingClaudeClient
├── RetryLoggingClaudeClient
├── RetryLoggingCachingClaudeClient
└── ...（OpenAI 側にも同じものが並ぶ）
```

しかも、リトライのコードは `RetryClaudeClient` と `RetryOpenAIClient` に重複する。

根本の問題は、「リトライつきのクライアント」は「クライアントの**一種**」ではない、ということだ。リトライは「クライアントの**呼び方**」の話だ。is-a ではないものを継承で表したので、無理が出た。

#### 合成で作る：同じ約束を持つ部品で包む

全員が `generate(prompt)` を持つ、という約束（ダックタイピング）を決める。リトライ・ログ・キャッシュは、**別のクライアントを中に持ち（合成）、自分も `generate` を持つ部品**にする。

```python
from typing import Protocol
import time


class LLM(Protocol):
    def generate(self, prompt: str) -> str: ...


# --- 本物のクライアント（ここでは偽物で代用） ---
class FakeLLM:
    def __init__(self, fail_times=0):
        self.fail_times = fail_times
        self.calls = 0

    def generate(self, prompt):
        self.calls += 1
        if self.calls <= self.fail_times:
            raise TimeoutError("timeout")
        return f"answer to: {prompt}"


# --- 部品：どれも inner を持ち（合成）、自分も generate を持つ ---
class Retry:
    def __init__(self, inner: LLM, times=3, wait=0.0):
        self.inner, self.times, self.wait = inner, times, wait

    def generate(self, prompt):
        for i in range(self.times):
            try:
                return self.inner.generate(prompt)
            except TimeoutError:
                if i == self.times - 1:
                    raise
                time.sleep(self.wait)


class Logging:
    def __init__(self, inner: LLM):
        self.inner = inner
        self.log = []

    def generate(self, prompt):
        self.log.append(prompt)
        return self.inner.generate(prompt)


class Cache:
    def __init__(self, inner: LLM):
        self.inner = inner
        self.memo = {}

    def generate(self, prompt):
        if prompt not in self.memo:
            self.memo[prompt] = self.inner.generate(prompt)
        return self.memo[prompt]


# --- 組み立て ---
fake = FakeLLM(fail_times=2)
llm = Cache(Logging(Retry(fake)))

print(llm.generate("挨拶して"))   # 2回失敗しても、Retry が3回目で成功させる
print(llm.generate("挨拶して"))   # 2回目はキャッシュから返る
print(fake.calls)                 # 3（2回失敗 + 1回成功。2回目の呼び出しは本物まで届いていない）
```

```
llm.generate("挨拶して")
   │
   ▼
 Cache ──(キャッシュに無い)──→ Logging ──(記録)──→ Retry ──(最大3回)──→ FakeLLM
   ▲                                                                      │
   └──────────────────────── 結果が戻ってくる ─────────────────────────────┘
```

- クラスの数は「クライアント2つ + 部品3つ」の **5つ**。機能が増えても、部品を1つ足すだけ
- どの部品も `generate` を持つので、**どの順番でも、どの組み合わせでも重ねられる**
- 部品を1つずつ `FakeLLM` を包んでテストできる

この形を**デコレータパターン**と呼ぶ。Python の `@デコレータ` 構文も、関数を包んで機能を足すという同じ発想だ。

#### 重ねる順番で、振る舞いが変わる

| 組み立て | キャッシュに当たったとき | 失敗したとき |
|---|---|---|
| `Cache(Logging(Retry(c)))` | ログもリトライも走らない（速い・ログに残らない） | 再試行は1回分としてログに残る |
| `Logging(Cache(Retry(c)))` | キャッシュに当たった呼び出しもログに残る | 同上 |
| `Retry(Logging(c))` | ― | 再試行のたびにログに残る |

「ログには本物の API を呼んだ回数を残したい」のか、「ユーザーからの依頼をすべて残したい」のか。要件によって正しい順番が変わる。順番を設計として意識することが大事だ。

#### 責務の分離

部品に分けたことで、それぞれのクラスが**1つの理由でしか変更されない**ようになった。

- リトライの回数や待ち方を変えたい → `Retry` だけを直す
- ログの出力先を変えたい → `Logging` だけを直す
- Claude の API が変わった → `ClaudeClient` だけを直す

これを**単一責任の原則**と呼ぶ。全部を1つのクラスに入れると、どの変更でもそのクラスを触ることになり、ある変更が別の機能を壊す危険が増える。

#### それでも継承を使うとき

継承が悪いわけではない。次のときは継承が自然だ。

- 本当に is-a のとき。例：`TimeoutError` は `OSError` の一種
- フレームワークが「このクラスを継承して、このメソッドを書いてね」と決めているとき。例：`unittest.TestCase`
- 親の振る舞いをほぼそのまま使い、一部だけ変えたいとき

迷ったら、「**子は親の代わりに、どこでも使えるか**」を考える。使えないなら、継承ではなく合成にする。

### よくある誤解

**`comp.inherit-for-reuse`：コードを再利用したいときは、まず継承を使うものだと思っている**

- 思い込み：既存のクラスの機能を使い回したい → そのクラスを継承する
- 実際：再利用の第一候補は合成。継承は「本当に親の一種か」が言えるときに使う
- 確かめ方：作ろうとしている子クラスについて「〇〇は△△の一種です」と文にしてみる。不自然なら合成にする

### 理解度チェック

- **言える**：is-a と has-a の違い
- **説明できる**：機能の組み合わせを継承で作ると、クラスの数が増える理由
- **使える**：上のコードに、プロンプトの先頭に決まった文（例：「日本語で答えて」）を付け足す部品 `Prefix` を足し、`Cache(Prefix(Retry(fake)))` と組み立てて動かす

## 入口の問題をもう一度

### q5：どれが `ask()` で動くか

> `ask` は `llm.generate` を探して呼ぶだけで、型や継承関係は見ていない。`ClaudeClient` と `FakeLLM` は自分で `generate` を持つ。`EchoClient` は `pass` だけで何も足していないが、探索で親の `ClaudeClient.generate` が見つかる。`OldClient` は `complete` しか持たないので `AttributeError`。答えは `ClaudeClient`、`FakeLLM`、`EchoClient`。

`FakeLLM` を外したのは、`duck.needs-inheritance`（継承していないと同じように扱えない）の思い込みから来ている。

### q6：property の嬉しさ

> `@property` とセッターを使うと、`client.temperature = 5` という普通の属性への代入の書き方のまま、代入のたびに検証を挟める。最初は普通の属性で書いておき、あとから検証が必要になっても、呼び出し側を書き換えずに済む。

最初の回答「不正な値の入出力を許容しなくなる」は、検証という使い道だけを挙げていた（`prop.only-validation`）。呼び出し側の書き方が変わらないことが、property ならではの価値だ。

### q8：リトライ・ログ・キャッシュの設計

> 全クライアントに `generate(prompt)` を持たせる約束（Protocol）を決める。リトライ・ログ・キャッシュは、別の `LLM` を中に持ち、自分も `generate` を持つ部品（合成、デコレータパターン）にする。継承で全組み合わせを作るとクラスが「クライアント数 × 機能の組み合わせ」で増えるが、部品なら機能の数だけで済む。重ねる順番で挙動が変わる（キャッシュを外側に置けば、当たったときにログもリトライも走らない）。部品ごとに `FakeLLM` を包んでテストできる。

演習の観点（rubric）の5項目が、すべてこの説明に入っていることを確かめよう。

## 隣の概念

- **抽象基底クラス（`abc.ABC`）**：Protocol と違い、継承を前提に「このメソッドを必ず実装すること」を強制する
- **Python のデコレータ構文**（`@functools.wraps` など）：関数を包んで機能を足す。この章の Retry を関数版で書くこともできる
- **ミドルウェア**：Web フレームワークの、リクエストを順に包んで処理する仕組み。合成の考え方そのもの
- **依存性の注入**：使う相手を外から渡す設計。テストのしやすさに直結する

## 理解度チェックの答え

### 基本構文

- **言える**：`pass` は何もしないで次へ進む文。`return` は関数を抜けて値を返す文
- **説明できる**：Python はインデントでブロックを表すので、ブロックを空にすると構文が成り立たない。空にしたいときの穴埋めが要る
- **使える**：

  ```python
  class Planner:
      def plan(self, goal):
          pass
  ```

### ダックタイピング

- **言える**：型や継承関係ではなく、そのメソッドを持っているかで使えるかが決まること
- **説明できる**：`ask` が `llm.generate` を読むと、Python は `llm` のインスタンス → そのクラスの順に `generate` を探す。`FakeLLM` クラスに `generate` があるので見つかり、呼べる。継承関係はこの探索に関係しない
- **使える**：

  ```python
  def summarize(llm, text):
      return llm.generate(f"次の文章を3行で要約して:\n{text}")

  class FakeLLM:
      def __init__(self):
          self.prompts = []
      def generate(self, prompt):
          self.prompts.append(prompt)
          return "要約"

  def test_summarize():
      fake = FakeLLM()
      assert summarize(fake, "長い文章") == "要約"
      assert "長い文章" in fake.prompts[0]
  ```

### property

- **言える**：`@property` を付けたメソッドがゲッター、`@名前.setter` を付けたメソッドがセッター
- **説明できる**：普通の属性で書いていたクラスを property に変えても、呼び出し側の `obj.x = v` はそのまま動く。メソッドにすると `obj.set_x(v)` へ呼び出し側を全部書き換える必要がある
- **使える**：

  ```python
  class Client:
      def __init__(self, max_tokens=1024):
          self.max_tokens = max_tokens

      @property
      def max_tokens(self):
          return self._max_tokens

      @max_tokens.setter
      def max_tokens(self, value):
          if not isinstance(value, int) or value < 1:
              raise ValueError("max_tokens は1以上の整数")
          self._max_tokens = value
  ```

### 継承と合成

- **言える**：is-a は「〜の一種」で継承、has-a は「〜を持つ・使う」で合成
- **説明できる**：機能ごとに「付ける・付けない」があるので、組み合わせは機能の数に対して倍々に増える。継承では組み合わせ1つにつきクラスが1つ要るので、クラス数も倍々に増える
- **使える**：

  ```python
  class Prefix:
      def __init__(self, inner, prefix):
          self.inner, self.prefix = inner, prefix

      def generate(self, prompt):
          return self.inner.generate(f"{self.prefix}\n{prompt}")

  llm = Cache(Prefix(Retry(FakeLLM(fail_times=1)), "日本語で答えて"))
  print(llm.generate("挨拶して"))
  ```
