# AIエージェントをスクラッチで作る #9 〜24時間動かす〜

## はじめに

ここからは「作る」ではなく「動かし続ける」の話です。実務ではこちらの方が長く付き合うことになります。

```
Agentが止まった。誰が気付く？
ログはどこ？
Ctrl+Cで止めたら、途中のTaskはどうなる？
APIキーはどこに置く？
コンテナを消したら生成物も消えた
```

今回はこれを全部潰します。

---

## 起動方法の話（最初にこれを潰す）

[[Dockerfile]]にこう書きたくなります。

```dockerfile
CMD ["python", "application/runner.py"]
```

**動きません。**

```
Traceback (most recent call last):
  File "/app/application/runner.py", line 1, in <module>
    from agents.planner import Planner
ModuleNotFoundError: No module named 'agents'
```

手元で実験するとはっきりします。

```
$ python -m application.runner        # OK
$ python application/runner.py        # ModuleNotFoundError
```

理由は `sys.path[0]` です。

| 起動方法 | `sys.path[0]` |
|---|---|
| `python application/runner.py` | `/app/application` |
| `python -m application.runner` | `/app`（カレントディレクトリ） |

前者だと `/app/application` の中を探すので、その隣の `agents/` が見えません。

これは **[[Docker]]・[[GitHub]] Actions・Cronの3箇所で同じように出ます。** 全部 `-m` で統一します。

```dockerfile
CMD ["python", "-m", "application.runner"]
```

---

## 起動のきっかけは3種類

| 型 | 例 | 特徴 |
|---|---|---|
| Event | Watcher, GitHub Push | 変化した瞬間に動く。取りこぼしがある |
| Schedule | Cron, Actions schedule | 確実だが遅れる。取りこぼしを拾う |
| Service | 常駐プロセス, Bot, Web [[API]] | 待ち続ける。落ちたら誰かが起こす必要がある |

**どれか1つを選ぶのではなく、組み合わせます。**

- Watcher（Event）で普段は即応
- Cron（Schedule）で1日1回、取りこぼしを回収

前章で書いた通り、両方が同じ `run_once()` を呼び、Taskのidが冪等なので二重処理になりません。

## Docker

### Dockerfile

```dockerfile
# slim を使う（python:3.12 は約1GB、slim は約150MB）
FROM python:3.12-slim

WORKDIR /app

# requirements だけ先にコピーする。
# ソースを1文字直すたびに依存を再インストールしないため（レイヤキャッシュ）。
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# ログが即座に出るように（バッファされると docker logs に流れてこない）
ENV PYTHONUNBUFFERED=1

CMD ["python", "-m", "application.runner"]
```

3つポイントがあります。

1. **`requirements.txt` を先にCOPY**。`COPY . .` を先に書くと、ソースを1文字直すだけで全依存の再インストールが走ります
2. **`--no-cache-dir`**。pipのキャッシュがイメージに残るのを防ぎます
3. **`PYTHONUNBUFFERED=1`**。これが無いと、標準出力がバッファされて `docker logs` に何も出ず、「固まった？」と勘違いします

### volumeが無いと全部消える

```bash
docker run knowledge-agent      # 実行される
docker run knowledge-agent      # また最初から全部処理される
```

`state/` `outputs/` `logs/` は[[コンテナ]]の中に書かれます。**コンテナを消せば消えます。** 状態を持つAgentでこれは致命的です。

### docker-compose.yml

```yaml
services:
  agent:
    build: .
    environment:
      # APIキーはイメージに焼かない。ホストの環境変数か .env から渡す。
      LLM_BACKEND: ${LLM_BACKEND:-fake}
      GEMINI_API_KEY: ${GEMINI_API_KEY:-}
      WEBHOOK_URL: ${WEBHOOK_URL:-}
    volumes:
      - ./docs:/app/docs:ro       # 入力は読み取り専用
      - ./outputs:/app/outputs
      - ./state:/app/state
      - ./logs:/app/logs

  watcher:
    build: .
    command: ["python", "-m", "watchers.markdown_watcher"]
    environment:
      LLM_BACKEND: ${LLM_BACKEND:-fake}
      GEMINI_API_KEY: ${GEMINI_API_KEY:-}
    volumes:
      - ./docs:/app/docs:ro
      - ./outputs:/app/outputs
      - ./state:/app/state
      - ./logs:/app/logs
    profiles: ["watch"]
```

```bash
docker compose up --build agent          # 1回だけ実行
docker compose --profile watch up watcher # 常駐監視
```

`docs` に `:ro` を付けているのは、**入力を書き換えないことをDockerに強制させる**ためです。バグでdocsを壊す事故が構造的に起きなくなります。

## APIキーの扱い

**コードに書かない、イメージに焼かない、リポジトリに入れない。**

```python
GEMINI_API_KEY = os.getenv("GEMINI_API_KEY", "")
```

`.gitignore` にこれを入れます。

```
.env
logs/
__pycache__/
```

GitHubの公開リポジトリにAPIキーを push すると、**分単位で自動収集ボットに拾われます。** 「すぐ消したから大丈夫」は通りません。git履歴に残ります。誤って上げたら、まずキーを失効させてください。

## Cron

### Linux / macOS

```bash
crontab -e
```

**crontabは1エントリ1行です。** よくある間違いがこれ。

```cron
0 2 * * *
cd ~/knowledge-agent
python -m application.runner
```

3行に分けると構文エラーです。正しくはこうです。

```cron
0 2 * * * cd ~/knowledge-agent && /usr/bin/python3 -m application.runner >> logs/cron.log 2>&1
```

3つ注意があります。

1. **`python` は見つかりません。** cronのPATHは最小限です。`which python3` で調べた絶対パスを書きます。venvなら `~/venv/bin/python`
2. **環境変数も引き継がれません。** `GEMINI_API_KEY` はcrontab内で定義するか、スクリプトで読み込みます
3. **標準出力は捨てられます。** リダイレクトしないと、失敗しても何も残りません

### Windows

タスクスケジューラを使います。「操作」に以下を設定します。

- プログラム: `C:\...\python.exe`
- 引数: `-m application.runner`
- 開始場所: `C:\...\knowledge-agent` ← **これを忘れると `-m` でも失敗します**

## GitHub Actions

### .github/workflows/agent.yml

```yaml
name: knowledge-agent

on:
  push:
    paths:
      - "docs/**"          # 資料が変わったときだけ動かす
  schedule:
    # 注意: GitHub Actions の cron は UTC。
    # 下は 17:00 UTC = JST 翌 02:00。日本時間で書くと9時間ずれる。
    - cron: "0 17 * * *"
  workflow_dispatch:        # 手動実行も残しておくと検証が楽

permissions:
  contents: write           # 生成物をコミットして戻すために必要

jobs:
  generate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - run: pip install -r requirements.txt

      - run: python -m pytest -q

      - name: Run agent
        env:
          LLM_BACKEND: gemini
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
        run: python -m application.runner

      - name: Commit outputs
        run: |
          git config user.name  "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add outputs state
          git diff --staged --quiet && echo "変更なし" && exit 0
          git commit -m "chore: update generated outputs [skip ci]"
          git push
```

### ハマりどころを4つ

**① cronはUTC**

`- cron: "0 2 * * *"` は日本時間の朝11時です。JST 2時にしたいなら `0 17 * * *`。ここは全員が一度は間違えます。

**② Secretsを渡さないと動かない**

```yaml
env:
  GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

これが無いと認証エラーで落ちます。リポジトリの Settings → Secrets and variables → Actions で登録します。

**③ コミットして戻さないと成果物が消える**

Actionsのランナーは実行後に破棄されます。`outputs/` に書いても、誰も見られません。コミットして push するか、`actions/upload-artifact` で残します。

**④ `[skip ci]` が無いと無限ループ**

`on: push` で起動し、最後に push する。**これは自分で自分を起動します。** 第7章のWatcherの自己ループと同じ構図です。

- `[skip ci]` をコミットメッセージに入れる
- `paths: docs/**` で発火条件を絞る

両方やっておくと安全です。

**⑤ scheduleはデフォルトブランチでしか動かず、60日無活動で止まる**

これは仕様です。動かなくなったら疑ってください。

## ログ

### `logging.info()` は何も出力しません

```python
import logging
logging.info("Task開始")
```

これを実行しても**何も出ません。** root loggerの既定レベルが `WARNING` だからです。

```python
>>> logging.getLogger().getEffectiveLevel()
30      # WARNING
```

「動いていない」と勘違いして数十分溶かす、定番の罠です。

### application/logging_setup.py

```python
import logging
import sys
from logging.handlers import TimedRotatingFileHandler

import config


def setup_logging(level: int = logging.INFO) -> None:
    config.LOG_DIR.mkdir(parents=True, exist_ok=True)

    # Windowsのコンソールは既定 cp932。UTF-8へ寄せないと日本語ログが化ける。
    if hasattr(sys.stdout, "reconfigure"):
        sys.stdout.reconfigure(encoding="utf-8", errors="replace")

    fmt = logging.Formatter(
        "%(asctime)s %(levelname)-7s [%(threadName)s] %(name)s: %(message)s"
    )

    file_handler = TimedRotatingFileHandler(
        config.LOG_DIR / "agent.log",
        when="midnight",
        backupCount=14,
        encoding="utf-8",       # ← これが無いとWindowsで落ちる
    )
    file_handler.setFormatter(fmt)

    stream = logging.StreamHandler(sys.stdout)
    stream.setFormatter(fmt)

    root = logging.getLogger()
    root.setLevel(level)
    root.handlers.clear()
    root.addHandler(file_handler)
    root.addHandler(stream)
```

### `encoding="utf-8"` を省くとWindowsで落ちます

指定しないとロケール既定（日本語Windowsでは `cp932`）が使われます。

```
UnicodeEncodeError: 'cp932' codec can't encode character '\u2705'
```

絵文字や一部の記号でこうなります。「ログを出そうとして落ちる」という最悪の失敗をします。

### `%(threadName)s` を入れる

並列実行しているので、どのワーカーの発言か分からないとログが読めません。

```
2026-08-09 17:46:53 INFO [ThreadPoolExecutor-0_2] [177459817f49] quiz 合格 (2回目)
```

`[177459817f49]` はTaskのidです。**全ログにTask idを入れておく**と、1件を最初から最後まで追えます。並列環境では必須です。

### ローテーション

`TimedRotatingFileHandler` で日次に分け、14日ぶん残します。24時間動かすなら、ログは放っておくと際限なく育ちます。

## 通知

Agentが止まっても、誰も見ていなければ気付きません。

```python
from abc import ABC, abstractmethod


class Notifier(ABC):
    @abstractmethod
    def notify(self, message: str) -> None: ...


class LogNotifier(Notifier):
    """既定。まずはログに出るだけでよい。"""
    def notify(self, message: str) -> None:
        log.warning("[通知] %s", message)


class WebhookNotifier(Notifier):
    def __init__(self, url: str, timeout: float = 5.0):
        self.url = url
        self.timeout = timeout

    def notify(self, message: str) -> None:
        payload = json.dumps({"text": message}).encode("utf-8")
        req = urllib.request.Request(
            self.url, data=payload, headers={"Content-Type": "application/json"}
        )
        try:
            urllib.request.urlopen(req, timeout=self.timeout).close()
        except Exception as e:
            log.warning("通知に失敗しました（本処理は継続）: %s", e)
```

**通知の失敗でAgentを落とさないでください。** 通知は本業ではありません。Slackが落ちているときに、こちらまで止まる理由はありません。

抽象にしてあるので、既定は `LogNotifier`、`WEBHOOK_URL` があれば `WebhookNotifier` に差し替わります。LLMClientと同じ考え方です。

### 何を通知するか

全部のTaskの成否を飛ばすと、誰も読まなくなります。

- 通知する: 実行そのものが失敗した、失敗率が閾値を超えた、同じファイルが3日連続で失敗している
- 通知しない: 1件のリトライ、正常終了

## Graceful Shutdown

`Ctrl+C` や `docker stop` で止めるとき、処理中のTaskを放り出すと、状態が「running」のまま残ります。

```python
shutdown = threading.Event()


def _install_signal_handlers() -> None:
    def handler(signum, frame):
        log.warning("停止要求を受け取りました。処理中のTaskを終えてから終了します。")
        shutdown.set()

    signal.signal(signal.SIGINT, handler)
    if hasattr(signal, "SIGTERM"):
        signal.signal(signal.SIGTERM, handler)
```

ワーカーは、区切りのいいところで自分から降ります。

```python
for attempt in range(1, config.MAX_RETRY + 1):
    if shutdown.is_set():
        return Outcome(task, False, attempt - 1, ["停止要求により中断"])
    ...
```

**リトライの合間**でチェックしているのがポイントです。[[LLM]]呼び出しの途中では止まりません。1回の生成は終わらせてから、次のリトライへ行かずに降ります。

`docker stop` はSIGTERMを送り、10秒待ってからSIGKILLします。10秒で終わらないなら `stop_grace_period` を伸ばします。

そして最後に必ず保存が走るので、次回はそこから再開できます。

## 実運用のチェックリスト

- [ ] `python -m` で起動しているか（`python xxx/yyy.py` になっていないか）
- [ ] volumeで `state/` `outputs/` `logs/` を外に出しているか
- [ ] APIキーが環境変数から来ているか。`.gitignore` に `.env` があるか
- [ ] `logging.basicConfig` / `setLevel` でINFOを有効にしたか
- [ ] ログファイルに `encoding="utf-8"` を指定したか
- [ ] ログにTask idと[[スレッド]]名が入っているか
- [ ] Actionsのcronの時差（UTC）を確認したか
- [ ] Actionsで生成物をコミットして戻しているか。`[skip ci]` は入れたか
- [ ] SIGTERMで状態を保存して終われるか
- [ ] `max_workers` を明示したか

## 今回のポイント

- 起動は必ず `python -m`。Docker・Actions・Cronの3箇所で効く
- Dockerはvolume必須。無いと状態も生成物も消える
- APIキーは環境変数。コードにもイメージにもリポジトリにも入れない
- crontabは1行。PATHも環境変数も引き継がれない
- GitHub Actionsのcronは**UTC**。生成物はコミットして戻す。`[skip ci]` で自己ループを防ぐ
- `logging.info()` は既定では出力されない。ファイルには `encoding="utf-8"`
- 通知の失敗で本体を落とさない
- SIGTERMを受けたら、リトライの合間で降りて状態を保存する

## 設計者メモ

この章のコードには、AIが1行も出てきません。それでいて、実務で一番時間を使うのはここです。

「AIエージェント開発はAIより運用」と言われる理由は、**AIの部分は失敗が目に見えるのに対し、運用の失敗は静かだから**です。

- プロンプトが悪ければ、変な出力が出るのですぐ分かる
- volumeを忘れれば、動いているように見えて何も残らない
- ログレベルを間違えれば、動いているのに何も見えない
- cronの時差を間違えれば、意図と9時間ずれた時刻に動く

どれも例外を投げません。**静かに間違い続けます。** チェックリストを作る価値があるのはこのためです。
