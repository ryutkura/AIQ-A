# AIエージェントをスクラッチで作る #10 〜プラグイン化とテスト〜

## はじめに

Generatorを増やす手順が、いまはこうです。

1. `agents/generators/mermaid.py` を作る
2. `prompts/mermaid.md` を作る
3. `agents/generators/__init__.py` に1行足す
4. Checkerに検査関数を足す

3番を無くします。そして**「Runnerを触らなくてよい」を、主張ではなく実験で確かめます。**

後半はテストです。ここまで「DIにしておくとテストできる」と言い続けてきたので、回収します。

---

## いまの構造の何が問題か

素朴に書くとこうなります。

```python
if task.task_type == "quiz":
    generator = QuizGenerator(builder, llm)
elif task.task_type == "summary":
    generator = SummaryGenerator(builder, llm)
elif task.task_type == "mermaid":
    generator = MermaidGenerator(builder, llm)
```

Generatorを増やすたびにRunnerを書き換えます。これは **Open-Closed Principle（拡張には開き、修正には閉じよ）** に反しています。

段階的に外していきます。

---

## Step 1: Strategy — 共通の形を決める

まず、全Generatorが同じ形をしていることを型で表明します。

```python
from abc import ABC, abstractmethod


class Generator(ABC):
    task_type: str = ""

    def __init__(self, builder: PromptBuilder, llm: LLMClient):
        self.builder = builder
        self.llm = llm

    @abstractmethod
    def generate(self, task: Task, attempt: int) -> Artifact:
        raise NotImplementedError

    def _call_llm(self, task: Task, attempt: int) -> Artifact:
        prompt = self.builder.build(task)
        content = self.llm.generate(prompt)
        return Artifact(
            task_id=task.id, task_type=task.task_type, target=task.target,
            content=content, model=self.llm.name, attempt=attempt,
        )
```

共通処理は `_call_llm` に集約されているので、個別のGeneratorはこれだけです。

```python
class QuizGenerator(Generator):
    def generate(self, task: Task, attempt: int) -> Artifact:
        return self._call_llm(task, attempt)
```

**この段階では、まだ差が無いように見えます。** それでいいです。差が出るのは、たとえば「MermaidGeneratorだけは生成後に構文チェックのため`mmdc`を呼ぶ」といった要求が来たときです。そのとき `generate` をオーバーライドするだけで済みます。

> 注意: Strategyパターンを「なんとなく将来のために」入れるのは早すぎる抽象化になりがちです。今回は**すでに2種類ある**（quiz, summary）ので入れる価値があります。1種類しかないうちは、ただのクラスで十分です。

## Step 2: Factory — 生成を1箇所に

```python
class GeneratorFactory:
    def create(self, task_type, builder, llm):
        if task_type == "quiz":
            return QuizGenerator(builder, llm)
        if task_type == "summary":
            return SummaryGenerator(builder, llm)
```

Runnerからif文は消えました。**でもFactoryにif文が移っただけです。** まだOCPを満たしていません。

## Step 3: Registry — if文を辞書にする

if文の本質は「文字列からクラスへの対応表」です。ならば辞書にします。

```python
class GeneratorRegistry:
    _registry: dict[str, type[Generator]] = {}

    @classmethod
    def register(cls, task_type: str):
        def decorator(gen_cls: type[Generator]) -> type[Generator]:
            gen_cls.task_type = task_type
            cls._registry[task_type] = gen_cls
            return gen_cls
        return decorator

    @classmethod
    def known_types(cls) -> list[str]:
        return sorted(cls._registry)

    def __init__(self, builder: PromptBuilder, llm: LLMClient):
        self.builder = builder      # 依存は外から受け取る（DI）
        self.llm = llm

    def create(self, task_type: str) -> Generator:
        try:
            gen_cls = self._registry[task_type]
        except KeyError:
            raise ValueError(
                f"未登録の task_type: {task_type} "
                f"(登録済み: {', '.join(self.known_types()) or 'なし'})"
            ) from None
        return gen_cls(self.builder, self.llm)
```

登録はデコレータで書きます。

```python
@GeneratorRegistry.register("quiz")
class QuizGenerator(Generator):
    def generate(self, task, attempt):
        return self._call_llm(task, attempt)
```

**クラス定義のすぐ上に「これはquizです」と書いてある**のが良いところです。登録処理が別ファイルに散らないので、追跡できます。

### KeyErrorをそのまま漏らさない

```python
raise ValueError(
    f"未登録の task_type: {task_type} (登録済み: quiz, summary)"
) from None
```

素の `KeyError: 'mermaid'` だと、原因が分かりません。**「何が登録済みか」まで出す**と、`prompts/mermaid.md` を作り忘れた、import を足し忘れた、といった原因に即たどり着けます。

エラーメッセージは第5章でAI向けに書きましたが、こちらは**開発者向け**です。宛先が違うだけで、考え方は同じです。

### クラス変数とインスタンス変数を混ぜない

ここは実装ミスが起きやすい箇所です。

```python
_registry = {}                       # クラス変数。全体で1つ
def __init__(self, builder, llm):    # インスタンス変数。DIの依存
```

`create` を `@classmethod` にしてしまうと `self.builder` が無くなり、`TypeError: __init__() missing 2 required positional arguments` になります。**「登録はクラス単位、生成はインスタンス単位」**と覚えてください。

## Step 4: Dependency Injection と Composition Root

Generatorは `PromptBuilder` も `LLMClient` も自分で作りません。渡されます。

```python
class Generator:
    def __init__(self, builder, llm):     # 外から受け取る
        self.builder = builder
        self.llm = llm
```

依存を実際に組み立てる場所を1箇所に集めます。これを **Composition Root** と呼びます。

```python
class Runner:
    def __init__(self) -> None:
        config.ensure_dirs()

        llm = build_llm_client()                          # ここでだけ具体が決まる
        builder = PromptBuilder(config.PROMPTS_DIR, config.DOCS_DIR, ...)

        self.state_service = StateService(config.STATE_FILE)
        self.discovery = Discovery(config.DOCS_DIR)
        self.planner = Planner(task_types=GeneratorRegistry.known_types())
        self.generators = GeneratorRegistry(builder, llm)
        self.checker = Checker()
        self.store = ArtifactStore(config.OUTPUTS_DIR)
```

`Planner(task_types=GeneratorRegistry.known_types())` に注目してください。**Plannerに種類のリストをハードコードしていません。** 登録済みのGeneratorから自動で決まります。Generatorを1つ足せば、Plannerが作るTaskも自動で増えます。

> 厳密には、Composition Rootはエントリポイント（`main()`）であって `Runner.__init__` ではありません。ただ、Runnerが最上位なら実質同じです。**「新しい部品を足すとき、どこを見ればいいか」が1箇所に決まっている**ことが本質です。

## 実験：本当にRunnerを触らずに増やせるか

主張だけでは信用できないので、実際にやります。

**1. Generatorを作る**

```python
# agents/generators/flashcard.py
@GeneratorRegistry.register("flashcard")
class FlashcardGenerator(Generator):
    def generate(self, task, attempt):
        return self._call_llm(task, attempt)
```

**2. プロンプトを作る**

```markdown
<!-- prompts/flashcard.md -->
# 指示
以下の資料から暗記カードを作成してください。
{"cards": [{"front": "表", "back": "裏"}]}
```

**3. 検査を足す**

```python
VALIDATORS = {
    "quiz": _validate_quiz,
    "summary": _validate_summary,
    "flashcard": _validate_flashcard,     # ← 追加
}
```

**4. importを1行**（この後これも無くします）

実行します。

```
変更を検知: 3件
Taskを生成: 9件 (種類: flashcard, quiz, summary)
```

`application/runner.py` の変更行数を数えます。

```bash
$ grep -c flashcard application/runner.py
0
```

**0行です。** Planner、TaskQueue、Runnerのループ、State管理——どれも触っていません。Taskが4件から9件に増えたのは、`known_types()` が自動で拾ったからです。

## Step 5: importも自動にする（ただし慎重に）

`agents/generators/__init__.py` の1行も無くせます。

```python
import importlib
import pkgutil

import agents.generators as pkg

for module in pkgutil.iter_modules(pkg.__path__):
    if not module.name.startswith("_"):
        importlib.import_module(f"{pkg.__name__}.{module.name}")
```

`importlib.import_module` だけではフォルダを走査できません。**`pkgutil.iter_modules` とセット**です。

これで「ファイルを置くだけ」になります。ただし、私は**明示importを残すことを勧めます。**

| | 自動走査 | 明示import |
|---|---|---|
| 追加の手間 | ファイルを置くだけ | 1行足す |
| どこで登録されたか | 追いにくい | 一目で分かる |
| 壊れたファイル | 起動時に全部巻き添え | そのファイルだけ |
| import順の制御 | できない | できる |

「1行足す」は大した手間ではありません。一方、**プラグインが読み込まれない理由を深夜に探す**のは大した手間です。プラグインを第三者が提供する（配布する）場合は自動走査に価値がありますが、自分のリポジトリの中なら明示で十分です。

パターンを知った上で使わない判断ができることが、パターンを覚えることより大事です。

## テスト

ここまで「DIにしておけばテストできる」と言い続けてきました。回収します。

### なぜAIエージェントのテストが難しいと言われるか

- [[LLM]]の出力が毎回違う
- [[API]]を叩くのでお金と時間がかかる
- ネットワークが要る

**これは全部「LLMを直接呼んでいる」場合の話です。** 抽象の裏に隠してあれば、そこを差し替えるだけです。

```python
class ScriptedLLM(LLMClient):
    """あらかじめ決めた順に返すLLM。何を渡されたかも記録する。"""
    name = "scripted"

    def __init__(self, responses: list[str]):
        self.responses = list(responses)
        self.seen_prompts: list[str] = []

    def generate(self, prompt: Prompt) -> str:
        self.seen_prompts.append(prompt.to_text())
        return self.responses.pop(0) if self.responses else "{}"
```

`seen_prompts` を持たせているのがコツです。**「何を返したか」だけでなく「何を渡されたか」も検証できます。**

### 何をテストするか

LLMの出力品質はテストしません。**Harnessをテストします。**

| 対象 | テストすること |
|---|---|
| Checker | 壊れた出力を検出できるか。理由が具体的か |
| リトライループ | 失敗理由が次のPromptへ入るか。上限で止まるか |
| StateService | 保存・復元できるか。壊れても再開できるか。並列で壊れないか |
| Discovery | 追加・変更・削除を検出するか。一時ファイルを無視するか |
| Task | 同じ入力で同じidか（冪等性） |
| PromptBuilder | task_typeでテンプレートが切り替わるか。長文を切るか |

**どれもLLMを必要としません。** これがこの設計の見返りです。

### 実際のテスト

```python
def test_コードフェンス付きは落ちて理由が分かる():
    result = Checker().check(artifact(f"```json\n{valid_quiz()}\n```"))
    assert not result.ok
    assert any("コードフェンス" in e for e in result.errors)


def test_失敗理由が次のPromptへ差し込まれる():
    llm = ScriptedLLM(["```json\n{}\n```", valid_quiz()])
    outcome = build_runner(llm)._process(make_task())

    assert outcome.attempts == 2
    first, second = llm.seen_prompts
    assert "前回の出力は下記の理由で不合格" not in first
    assert "前回の出力は下記の理由で不合格" in second
    assert "コードフェンス" in second


def test_LLMが例外を投げても全体を落とさない():
    class BrokenLLM(LLMClient):
        name = "broken"
        def generate(self, prompt):
            raise TimeoutError("API timeout")

    outcome = build_runner(BrokenLLM())._process(make_task())
    assert not outcome.ok
    assert any("TimeoutError" in e for e in outcome.errors)


def test_並列に保存してもJSONが壊れない(tmp_path):
    svc = StateService(tmp_path / "STATE.json")
    svc.save(State())

    def worker(i: int) -> None:
        st = svc.load()
        st.seen[f"f{i}.md"] = str(i)
        svc.save(st)

    with ThreadPoolExecutor(max_workers=8) as pool:
        list(pool.map(worker, range(100)))

    json.loads((tmp_path / "STATE.json").read_text(encoding="utf-8"))
```

### pytest.ini

```ini
[pytest]
testpaths = tests
pythonpath = .
```

`pythonpath = .` を書いておくと、`tests/` から `models` や `services` が import できます。第9章の `sys.path` の話と同じ問題です。

```bash
python -m pytest -q
```

```

```

**1.2秒です。** APIキーもネットワークも要りません。だからCIで毎push回せます。

### 日本語のテスト名

```python
def test_失敗理由が次のPromptへ差し込まれる():
```

pytestは関数名をそのまま出すので、失敗したときに何が壊れたか一目で分かります。個人・少人数プロジェクトなら、これは実用的です。

## 今回のポイント

- Strategy → Factory → Registry の順にif文が消えていく
- Registryはデコレータ登録。クラス定義の隣に宣言が書ける
- エラーは「未登録の X（登録済み: A, B）」まで出す
- 登録はクラス変数、生成はインスタンス（DI）。混ぜると `TypeError`
- Composition Rootを1箇所に。`Planner(task_types=known_types())` で連動する
- 自動走査は可能だが、明示importの方が事故が少ない
- LLMを抽象の裏に置けば、Harnessは全部テストできる
- テストするのはLLMの品質ではなくHarnessの挙動

## 設計者メモ

Strategy・Factory・Registry・DIを別々のパターンとして覚える必要はありません。**全部「変更理由ごとに責務を分ける」の言い換え**です。

| 変更理由 | 分けた先 |
|---|---|
| 生成方法が種類ごとに違う | Strategy |
| どの種類を使うかが実行時に決まる | Factory / Registry |
| 使うLLMが環境で変わる | DI |
| 起動のきっかけが増える | Watcher / Cron |

パターン名を覚えるより、**「これは何の変更に備えているのか」を言えること**が大事です。言えないなら、そのパターンはまだ要りません。
